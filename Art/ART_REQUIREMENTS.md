# 项目美术需求与提示词规范 v2

更新：2026-11-11。适用范围：角色画像、表情差分、剧情 CG、物品图标。当前任务的具体要求优先于本规范；历史草案不能覆盖用户后来确认的造型。

本版将下巴覆盖与眼部位置问题纳入正式制作和验收要求。下颌保护已实现，眼部结构修正仍待实施；规范中的要求不代表当前资源已经全部通过。

## 1. 已验证的制作基础

角色先生成正常高分辨率母图，再用原作者 **B/detail** 配方导出游戏画像。原始说明保留在[图片生成提示词.txt](图片生成提示词.txt)，实现为[author_portrait_pipeline.py](../tools/author_portrait_pipeline.py)。

原作者样例已全部 RGBA 像素复现：288×212，共 61056 像素，0 差异；另通过 13 类边界检查、3 组独立二维面积积分验证和 7 张项目画像对照。详见[验证记录](author-pipeline-validation-2026-11-10/README.md)与[机器记录](author-pipeline-validation-2026-11-10/verification.json)。这是离线采样验证，不代替实机显示验收。

此前 Pillow BOX、固定 48/64 色、最近邻缩图和“主动画成大颗粒像素再压小”的方案均不作为新画像的默认制作标准。历史导出脚本仍可能使用 BOX；新工作应调用已验证实现，而不是照抄旧说明。

## 3. 画风与人物一致性

美化分支参考 `cute_portraits` 的对应阶段 Eleanor，不参考原版写实脸。她应保留橙色长卷发、绿眼、成熟面容与原有神态；不同服装仍是同一个人。**Lydia 日常美化 v4 已获用户最终确认**：成年27岁、琥珀眼、偏冷棕色长直为主且发尾轻弯，沿用作者画风及本项目衣裙、身材设计。

Lydia 的约会服、差分与后宫 CG 应继承[定稿记录](lydia-style-fusion-2026-11-10/README.md)和 `Art/lydia-style-fusion-2026-11-10/approved/lydia_daily_beauty_master.png`。旧约会服仅提供服装设计，不能重新带回旧脸型、卷发或较小胸围。日常v4、约会服v1及两套共10张新表情已成套更新到工作区美化资源；后宫CG以两人的上层区日常服为准，0.89采用用户确认的[蓝紫像素风定稿](route-endings-pixel-2026-11-11/ART_DELIVERY.md)，已替换运行占位。

原版分支在母图阶段就建立相应脸型、明暗、服装结构与克制的表现；不能把同一美化母图减色后当作另一套正式原版形象。已有原生资源可按已确认的回退方案复用，例如未启用美化时晚会复用原版上层区 Eleanor。

正常母图保留完整眼线、眼神、发束、肤色和衣物结构；不要求生成器模拟低分辨率方格、抖动、马赛克或碎点。细节应服从轮廓与体积，不能靠压缩修复错误眼睛、五官、人体或布料。

材质写成可观察特征：织物用细密织纹、柔和反光、接缝与受力；胶质/金属才使用相应高光。性感按本轮确认的剪裁、材质和成熟比例表现，不自动改服装，也不把所有衣服变成胶衣。当前革命军候选为黑色带轻微透感的战术布料，胸前通过承托剪裁表现挺拔聚拢；它不是全项目人物的默认服装。

布料透感是绘制在人物上的色彩与光影，不能把胸腹人物实体变成透明 PNG 像素，让店铺背景透穿身体。

## 4. 画像构图

正式画像为 **288×212、8 位 RGBA PNG**。母图分辨率由生图输出决定，不能把整张大图直接非等比拉伸成游戏尺寸。

母图画到腰部，不代表最终 288×212 必须容纳整条腰线。游戏画像优先与既有角色匹配脸部大小、眼睛和下巴位置，躯干可延伸到下沿之外。禁止为了容纳整套衣服而缩小脸。

Eleanor / Lydia 同类成年美化画像的近似核对点为眼部中线 y≈115、下巴 y≈138、脸颊宽约 36 像素；原版对应参考约为 y≈98、y≈127、38 像素。它们是人工核对参照，不是所有角色、年龄、姿势的固定模板。母亲或明显不同姿态应另建参数。

现有已验证候选参数如下，**Yb 是补顶行之前的采样坐标**：

| 图像 | Ht | Cx | Yb |
| --- | ---: | ---: | ---: |
| Eleanor 女仆美化 | 182 | 143 | 233 |
| Eleanor 礼服美化 | 209 | 143.5 | 266 |
| Lydia 日常/约会原版，待重设时重校准 | 174 | 143.5 | 215 |
| Lydia 定稿日常美化 v4 | 152.116651 | 144.934619 | 215 |
| Lydia 约会美化 v1 | 152.696143 | 145.079492 | 215 |
| 革命军黑色战术服 v3 候选 | 220 | 139 | 281 |
| 作者玫瑰角色复现样例 | 150 | 144.5 | 211 |

Ht 指整个人物透明包围盒等比缩放后的高度，可能被最终画布裁掉一部分。150 不是全员通用高度；Yb 也允许超出画布。

Lydia 新日常与约会的源包围盒略有不同，上表的 Ht/Cx 因此不同；它们实际共用 `s=0.14487300094073377, tx=38.81514581373473, ty=59.11665098777047`。表情沿用此映射，不能因为睁眼后虹膜可见面积增加而重新缩放人物。

## 5. 表情差分

### 5.1 基础像与改动范围

一个人物、一套服装、一个风格分支构成一个表情族。必须使用其真正的中性底图，而非另一种画风的同名人物。

| 部位 | 固定内容 | 允许的表情变化 |
| --- | --- | --- |
| 眼睛 | 内外眼角位置、横向跨度、双眼间距与双眼连线倾角、虹膜设计 | 上下眼睑开合；剧情需要且明确记录的视线移动 |
| 眉部 | 与同一张脸的结构关系、原有画风 | 眉形、高低、收紧或放松，逐眉核对 |
| 嘴部 | 嘴在脸上的位置、成年面貌与原有画风 | 嘴形、开合、笑意等，不能带动下巴或拉长下半脸 |
| 面部结构 | 脸型、下颌线、头部角度、鼻子位置与人物身份 | 所需脸红或局部表情明暗 |
| 其余区域 | 头发、首饰、颈部、身体、服装、尺寸、位置和光照 | 本次仅制作表情时保持不变 |

表情应能在原生尺寸读出情绪，不用同一个微笑加不同文件名充数。双人CG分别指定两人的眉形、眼睑和嘴形，避免同一套浅笑；例如后宫CG当前候选为Eleanor羞怯期待、Lydia明朗主动，不能自动扩展为所有场景的固定表情。

Lydia 中性像略收眼睑，表现见过世面的从容。smile、flustered 可通过抬高上眼睑适度睁眼；serious 更专注，hurt、tease 保持收敛。保持眼角、眼睛横向跨度、虹膜设计与成年感，不能用扩大整只眼睛或缩放脸部替代情绪变化。

### 5.2 眼部对齐与重制条件

先在**实际中性PNG**记录左右眼内外眼角、眼间距及双眼连线，再核对生成母图和最终成图。坐标须注明来自高清母图还是288×212画布，记录母图至原生画布的映射及实际采用的局部变换。

绿色虹膜像素的重心只能提供候选位置，不能作为唯一结构锚点。眼睑遮挡、高光、暖色反光及缩小采样会改变色块位置；闭眼或暖色虹膜还可能检测失败，甚至把同一只眼分成两组。检测结果须确认确为左右两只眼，异常结果不直接用于自动缩放或报告真实位移。

整体缩放与平移只匹配距离和中点，不能消除倾角差、单眼形变或眼角漂移。修正应在面部层内逐眼校准位置、大小和倾斜，眉部单独处理；鼻子、嘴和头部不随眼部修正整体搬动。不能因为睁眼后可见虹膜面积增加而重新缩放人物。固定整图映射也不等于源图内部五官没有移动。

原生切换时，眼角、眼间距和眼睛在脸上的位置应保持稳定；眼睑开合须符合情绪。不能用“偏差不到一个像素”直接判定合格，半像素的采样差异也需在游戏实际放大倍率下查看。若生成已经改变眼型、成年感或人物身份，或只能靠大幅拉伸才能对齐，应重做该差分。

### 5.3 面部装配与内部结构保护

本项目采用“生图创作面部 → B/detail采样 → 面部图层装配”。身体和alpha沿用同族中性底图，不接受生成器重画产生的身体漂移。

下颌是角色不透明区域内的结构边界，alpha相同不能证明下巴未改变。两个表情导出器均通过 `tools/expression_face_bounds.py` 将替换层限制在基础像的脸部内部，羽化只能向内，不能覆盖下颌线和颈部。新增服装或构图要人工重设边界，不能沿用旧画像坐标。`tools/check_expression_jaws.py` 使用独立选取的下颌/颈部像素区作回归检查，同时确认表情仍存在、眼眉未被修复改写。原因及修复对照见[下巴覆盖修复记录](expression-chin-fix-2026-11-10/ART_DELIVERY.md)。

眼部替换边界还须检查新眼线是否完整进入图层、旧眼线是否残留在图层外，以及羽化后有无双重眼线、断线或混合眼角。不能只画一个统一椭圆就认定所有表情都适合该范围。羽化仅作窄范围接缝过渡，不对整张脸模糊来掩盖位置错误。

### 5.4 验收与当前实现状态

1. 对照对象注明为“当前差分与中性基础像”或“修复后差分与修复前差分”。“眼眉保持不变”若只指后者，不能解释为眼部已经与基础像对齐。
2. alpha与中性图逐像素相同；面部允许区域外的可见RGB相同；独立检查下颌线、颈部等不透明区域内的结构边界。
3. 原生1倍、最近邻整数放大、游戏实际显示倍率下切换neutral与各表情，检查眼角、鼻子、下巴、头顶、肩膀、衣物和道具。表情应有区别，位置不抖动。
4. 同时查看眼角标点、半透明叠加和合成接缝。叠加用于发现问题，不能把正常眼睑变化产生的重影一律判为错位；最终结合稳定结构点人工判断。
5. 当前运行时只有美化分支启用差分；缺图回退基础像。新增资源键须与 `PortraitExpression` 对应，切换回neutral不得突然变成旧脸或旧服装。

## 6. B/detail 导出约定

1. 原始母图永久保留；已有正确 alpha 直接使用。只有确为洋红底才启用原配方的强/弱背景与邻域清理，抠图阶段只改 alpha。
2. 用 alpha≥128 求半开包围盒 `[x0,y0,x1,y1)`；令 `s=Ht/(y1-y0)`，`tx=Cx-s*(x0+x1)/2`，`ty=Yb-s*y1`，横纵共用同一个 s。
3. 洋红除色须显式选择：有污染时按原配方检查源图内 4 像素轮廓带；干净透明且含合法紫色的素材可关闭。记录选择和依据，保留对照。
4. 精确累计目标像素对应源矩形的相交面积，仅 alpha≥128 的源像素参与 RGB 平均。覆盖率≥0.35 时输出 alpha=255，否则 0。使用 8 位 RGB 数值域，`floor(v+0.5)` 取整。
5. 仅对中心和四邻域全不透明的非边框像素作一次 detail：`abs(delta)>6` 才加 `0.35*delta`，所有读取来自同一未增强副本。
6. 必要时作目标图内 1 像素同配方除色。按上、下、左、右四邻域传播不透明 RGB 到透明区，alpha 仍为 0。
7. 在 288×211 完成采样，然后原样复制到新 288×212 的 `(0,1)`；新顶行为 `(0,0,0,0)`。已经完成补行的 PNG 不再补行或重新缩放。

除色距离只考虑图内真正透明的像素，被裁在画布底边的衣服不是透明轮廓；只有采样计算把源图外视作透明。透明区 RGB 扩展是正确输出，不能要求所有透明 RGB 清零。

保持丰富 RGB，不固定压成 32/48/64 色、不加抖动、不反复锐化、不自动删除小连通块。PNG 负责无损保存，不能把 JPEG 或聊天截图当作正式母图。

## 7. CG 与物品分别交付

CG 必须从当前结局文本取场景，不擅自增加婚礼、宫殿、人物或路线事件；玩家外观未设定时可采用玩家视角。完整画幅绘制人物与环境，预留实际 UI 的文字区域；没有明确要求不生成文字、标志、UI。

侍从/后宫正式CG为用户确认的蓝紫/珊瑚色像素风、960×540、16:9完整不透明场景，详见[0.89交付记录](route-endings-pixel-2026-11-11/ART_DELIVERY.md)。该CG分支以原游戏结束图与已选革命军CG为画法依据，优先于画像默认的平滑母图要求。CG采用整幅等比面积采样，不使用画像人物高度、不补画像顶行、不加固定减色、后期抖动或锐化。0.89即时结局页上图下文、图片保比例；旧档GameOver背景图也改为保比例。不同画幅和实机文字显示仍需核对。旧[后宫v3](harem-ending-2026-11-10/ART_DELIVERY.md)保留为历史候选，不再是当前正式版本。

物品先确认实际网格与显示比例，不能从 64×64 原图推断占位大小。现有手工镯为 2×1、吊坠 2×2、橱窗信物 1×1；分别有运行时裁切与 PPU 缩放。轮廓必须与实际占位、同框牙膏等实物尺度相符，避免蛇形占位或把手镯扩大成 4×2。图标不套用画像画布及排布参数。

## 8. 交付与验收

新美术按 `Art/<主题-日期>/masters/`、`prompts/`、`portraits/` 或 `endings/`、`previews/` 存放。保存实际提示词、参考图角色说明、生成方式、输入/输出 SHA256、源包围盒、排布参数、除色选择与版本状态。参考原图本地保存，不混入工坊包；历史资源不直接删除。

文件名与运行资源键一致；差分采用 `er_expr_<实际基础键>_<表情>.png`。候选只有获得当前任务的替换指令后才写入 `Textures/Items`；发布是独立动作，按用户本轮指令执行。

验收顺序：母图五官与材质 → 原生 1 倍 → 最近邻 3/4 倍边缘 → 白/黑/#252C35 背景 → 同框和表情切换 → 文件/资源键 → 实机 UI。文件存在、算法通过、审美通过、运行验收是不同结论，报告须如实区分。

交付记录须分别写明：比较的两份文件及其哈希、眼角等标点的坐标来源、采用的整体/局部变换、面部替换范围、实际看过的原生/放大/叠加预览、各检查的结果与局限，以及尚未处理的问题。自动识别失败或估读值不得包装为精确人体测量。视觉问题尚未解决时，其他检查通过仍保留该问题的待办状态。

“工作区已替换”“本地游戏已同步”“工坊已发布”分别记录。匹配本地旧文件哈希后的修复同步需备份并保留清单；运行中的精灵可能有缓存，重启后才进行实际显示验收。导出命令和内容键检查通过不等于已经在游戏中观察结果。
