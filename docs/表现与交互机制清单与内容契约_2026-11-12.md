# 表现与交互机制清单与内容契约

日期：2026-11-12
版本：v1.5（草案，待用户确认；按章 beat 分节的逐行脚本）
性质：当前内容机制的总清单、准入规则与冲突裁决。它不是新功能提案，不修改 Content、src、Localization 或游戏文件。
适用范围：共同/常规、侍从、双恋/后宫、革命军、互动、日常、结局页、UI 文案、场景卡、AI 写作提示词，以及后续任何新增表现或交互。

> 状态说明：本文件确认后，取代 `docs/文风与玩家台词基准_2026-11-10.md` 第 10 节中与本文件冲突的“本轮”规则；第 10 节的其余规则、非台词审计、原生机制评估、人设基准、美术规范、路线图规则和安全兼容文档继续有效。详细审计保留为证据，不删除。

## 内容分级（2026-11-13）

- 本项目按**成熟向（Mature）**处理，不再以“全年龄”自我标注。
- 最低合规：**不直接出现 R18/露骨性场景**；允许成熟主题、性张力、暗示与非露骨身体描写。
- 角色/路线卡可以保留更严格的阶段边界（如早期不确认恋爱、不写亲密身体关系），但不得再用“全年龄”作为项目级承诺。
- Steam Workshop / Nexus / site 文案按平台要求设置成熟内容标记与年龄提示。

## 0. 一页结论

1. 本 MOD 不是“没有机制约束”，而是约束散落在文风基准、非台词审计、原生机制评估、人设基准、美术规范、路线图和安全文档中，且部分规则已被后续发布超越。现在需要一份当前有效的总契约。
2. 默认只使用“原生机制 + 已批准扩展”；试点期间不新增机制。候选机制未批准前，不得写进正文。
3. 现有 `narrator` 主要用于系统提示/流程提示，不是场景叙述者。禁止旁白说话、解释设定或交代系统前提。
4. 裸 `*...*` 不是动作渲染指令，可能原样显示星号。新内容不再使用裸 `*...*` 做动作或旁白；短动作使用 `<i>...</i>`，长动作改成角色台词、通告或删除。
5. 逐句表情已上线，但仅限美化分支和当前可见客户；结局页已上线，但目前只用于 E3/E4 完美结局。它们不是“任何场景都能用”的通用按钮。
6. 独立无名动作行（舞台动作层）是候选机制，不是当前机制。试点不使用；如果确实需要，登记 `MECHANISM_REQUEST`，先做 spec 和垂直切片，经用户批准后才进入契约。
7. 试点 c01–c03 的默认机制集：角色对白、玩家选择、行内 `<i>`、表情（美化分支）、交易行为、必要时短通告/新闻。默认不使用独立动作行、实时演出、新 UI 或新 speaker。
8. 判断标准不是“这个机制能不能用”，而是“这个机制在什么场景、以什么形式、不能做什么”。机制清单是“能力 + 适用场景 + 禁止用法”，不是功能愿望单。

## 1. 术语、状态与优先级

### 1.1 术语

| 术语 | 定义 |
|---|---|
| 机制 | 可重复使用的表现或交互能力，分为引擎/UI 机制与叙事机制。前者决定“游戏能显示/接受什么”，后者决定“场景怎么写”。 |
| 原生机制 | 原版游戏已经提供、MOD 不需要新开发的能力。 |
| 已批准扩展 | 本 MOD 已经开发、测试并发布的机制。可用，但有明确适用范围。 |
| 候选机制 | 尚未批准的新机制。不得在正文中使用；需要 spec、垂直切片和用户批准。 |
| 禁止/超范围 | 不在本次写作重构范围内，或违反原作表现边界的能力。 |
| 行内动作 | 写在角色台词里的 `<i>...</i>` 短动作/语气提示。原作常用，本契约批准。 |
| 独立动作行 | 单独成句、没有角色姓名的舞台动作/环境提示。原版没有；本契约中仍是候选。 |
| 旁白 | 作者视角的叙述声音。禁止说话、解释设定或交代系统前提。 |
| 演出 | 实时灯光、音效、镜头、角色动画等视觉/音频表演。文本行不是演出。 |
| 叙事机制 | 场景契约、选择→回应→合并、可选说明、短动作拍等写作规则，不是引擎功能。 |

### 1.2 状态标记

|---|---|---|
| N | 原生机制 | 可用，按原生限制 |
| A | 已批准扩展 | 可用，按本文件范围 |

### 1.3 优先级

1. 用户已确认的剧情、路线、角色与玩法决定。
2. 本文件（当前内容机制契约）。
3. 现有详细审计与规范：文风基准、非台词审计、原生机制评估、人设基准、美术规范、路线图、安全兼容。
4. AI/写手的偏好与便利。

如果代码行为与本文件冲突：代码是“实际发生了什么”的证据，本文件是“允许怎么用”的规则；必须显式更新其中一方，不能静默绕过。

## 4. 关键机制的使用边界

### 4.1 行内 `<i>` 短动作

- 用途：角色自己在说话时的一个极短动作/语气，例如 `<i>瞥了一眼门外</i>`、`<i>把下巴抬高</i>`、`<i>叹气</i>`。
- 试点配额：每场景/来访 1–2 条；每条 2–8 字目标，最多 16 字；不连续；不整段斜体；不在同一情绪点叠加多个效果。
- 长动作、环境变化、第三方动作不塞进 `<i>`；先尝试角色台词，再尝试通告/新闻/Paper Book；都不行才登记动作行候选。
- 该配额暂时放宽 `文风基准§10` 的“每章最多 1 条”，因为旧配额与“场景没有身体”的问题直接相关。试点结束后复核永久配额。

### 4.2 逐句表情

- 只对当前可见客户；只影响正在说话的角色；不给不在场角色换表情。
- 只在美化分支生效；原版分支使用基础立绘。缺图回退基础像。
- 用于关键情绪拍，不逐句滥用；不把表情当台词，不用表情替代行为和选择。
- 服装变体在来访/场景开始选定；不做中途换装。
- 美术资源、表情族、回退和检查按 `Art/ART_REQUIREMENTS.md`。

### 4.3 玩家选择

- 每个来访 3–5 个选择点；每点 2–3 个选项；标签 2–8 字。
- 每个选项必须有不同即时回应；至少一个选择改变事实、信息、关系或后续对话。
- 不用选择伪装自由文本；不写引擎无法执行的选项；不让所有选项立刻合并成同一句而无差别。
- 选项标签和回应都要进入本地化；选项回显与菜单含义一致。

### 4.4 通告/新闻/Paper Book

- 通告、新闻是叙事内的信息来源，不是作者旁白；用于巡逻、判决、市场、撤案等世界事实。
- 短、具体、可核对；不写心理分析、关系总结或系统规则。
- Paper Book 用于文件、账本、纪念物、新闻剪报；需要美术和本地化；不替代核心对白。
- 同一信息不要同时用通告、新闻、对话重复三遍。

### 4.5 自定义 speaker

- 只用于真实角色或叙事内信息来源；必须有明确姓名/身份和正确的对话框归属。
- 新闻/治安通告是来源型 speaker，不是旁白；不能用来解释角色内心或系统规则。
- 新增 speaker 属于机制变更，需要批准；不能为了临时场景随手加一个“旁白角色”。

### 4.6 短旁白/动作行（A-D8）与更长动作层（C-D8）

- A-D8 已按试点批准：只允许 `[旁白|文本]` 单行；1–3 条/场景；每条 ≤40 字；只写镜头可见/可听的动作、环境、道具互动；不写日期/章节/心理/关系总结/设定解释/系统规则；不是会说话的旁白。
- 所有非对白叙述必须带 `[旁白|...]`；未标记的叙述段落不合格。
- 它不是角色：没有名字、没有人格、不发表观点、不解释设定；转换层映射为短旁白/动作行，UI 可显示“旁白”或隐藏姓名。
- 更长的独立动作/舞台动作层（C-D8）仍候选；需 spec/垂直切片；实时演出仍禁止。

### 4.7 原生剧情/交易钩子

- 使用前确认它确实是可用接口，不根据枚举或旧攻略推断。
- 独立 ID、阶段、提交标志；旧档不补演；失败可重试；不覆盖官方晨间、执法和当前对话优先级。
- 不调用原角色专用方法来假装发生埃莉诺剧情；不篡改原版角色标记。
- 未使用的交易模式（BARTER、SELLNBUY、整单批发、货包切换、参数验收等）是候选，不是默认能力；需要 spec 和兼容验证。

### 4.8 结局页/路线 UI

- 结局页目前只用于 E3 侍从完美和 E4 后宫完美；其他结局用原生 GameOver。
- 扩展结局页需要：新规则、美术、路线图更新、旧档兼容和用户批准。
- 路线专属 UI 只用于对应路线；不搬到共同线；不改路线/结局时不更新 E 编号。

## 6. 内容契约

### 6.1 场景卡必须声明机制

每个场景卡/block 在写作前必须列出：

```yaml
mechanisms:
  - dialogue          # 角色对白
  - player_choice     # 原生选择菜单
  - inline_action_i   # 行内 <i> 短动作
  - expr              # 当前可见客户表情（美化分支）
  - trade             # 原生交易行为
  - security_notice   # 可选：治安通告/新闻
mechanism_requests: []  # 需要但未批准的机制；没有就留空
```

规则：

- `mechanisms` 只能填本文件 §3 中状态为 N/A 的条目。
- 需要 C 条目时，不写替代方案，填 `mechanism_requests` 并登记。
- 有 X 条目直接判定不合格，退回。
- 场景卡没有机制声明，不进入写作阶段。

### 6.2 AI 写作输入与输出

输入必须包含：

1. 本文件的“允许机制/禁止机制”摘要。
2. 场景卡、角色阶段、路线状态、已成立事实。
3. 机制声明和 `mechanism_requests`。
4. 现有文本中不能改的原作台词/保护行。
5. 本地化键、分支集合、占位符、旧档兼容要求。

输出必须满足：

- 只使用已声明且已批准的机制；不新增 speaker、UI、物品、场景、演出、能力。
- 不写会说话的旁白；不用裸 `*...*`；不写长动作塞气泡。
- 行内 `<i>` 在配额内；表情只在可见客户/关键拍；选择有不同回应。
- 需要未批准机制时，输出 `MECHANISM_REQUEST` 并停在该场景，不擅自找替代。
- 中文和英文同步；选项标签与回显一致。

### 6.3 MECHANISM_REQUEST 模板

```yaml
mechanism_request:
  scene: c01.b000
  player_experience: "玩家需要先感到门外有治安巡逻的压力，再听到埃莉诺开口"
  existing_attempts:
    - "埃莉诺台词 + <i>瞥了一眼门外</i>"
    - "治安通告短句"
  why_insufficient: "角色只能说她看见的；通告无法表现‘灯扫过’的即时感"
  frequency: "c01–c03 预计 1 次；若每章都有，属于系统需求"
  proposed_mechanism: "独立无名动作行（C-D8）"
  fallback: "保留埃莉诺的 <i> 动作 + 一句关于巡逻灯的台词，不新增机制"
  risk_scope: "仅文本层，无实时演出；需要 UI 隐藏姓名、历史灰字、实机测试"
  owner: "待指定"
```

规则：没有 `why_insufficient` 和 `fallback` 的请求不进入评估；能用现有机制解决的请求直接驳回。

### 6.4 试点机制预算

- 默认：不新增机制。
- 不新增：独立动作行、实时演出、语音/音效、自由文本、新 UI、新 3D 场景、新 speaker、新 TextAnimator。
- 允许：N-D1–N-D5、A-D7、N-P1、A-P2、N-C1、N-C2、N-C4、A-C5、A-C9（仅结局相关）、A-C10（仅元机制）。
- 动作拍：每场景/来访 3–4 个；其中 `<i>` 1–2 条；其余用道具、交易、表情或通告。
- 选择：每来访 3–5 个选择点；每点 2–3 个选项；至少一个改变事实/信息。
- 试点结束后再决定是否提出一个候选机制（最多一个）；试点期间不使用它。

### 6.5 审查清单

1. 场景卡是否声明了机制？有没有未声明的机制偷偷出现？
2. 是否使用了 C 或 X 条目？如果有，是否已登记/退回？
3. 裸 `*...*` 新增是否为 0？旧内容是否在触碰时迁移？
4. `<i>` 是否在 1–2 条/场景、2–8 字目标（最多 16 字）、不连续的配额内？
5. 表情是否只用于当前可见客户、关键情绪拍、美化分支？是否缺图回退？
6. 选择是否有不同即时回应？是否至少一个改变事实/信息？有没有换皮选项？
7. 通告/新闻/Paper Book 是否是场景内信息来源，而不是作者旁白？
8. 是否出现旁白说话、长动作塞气泡、实时演出描述、未批准的新 UI/speaker/物品？
9. NPC 是否只知道自己能知道的事？有没有把玩家没说过的话安到他头上？
10. 场景是否有外部事件、具体欲望、阻碍和事实变化？没有就重写或删除。

### 6.6 机制选择顺序

1. 角色能看见/能做到 → 角色台词 + `<i>` + 表情。
2. 角色看不见/说不出，但有世界内来源 → 通告/新闻/Paper Book。
3. 这是玩家的动作/态度 → 原生选择菜单/交易行为。
4. 以上都不行，且这个拍反复出现 → 登记 `MECHANISM_REQUEST`。
5. 只出现一次且无法承载 → 删除该拍，或接受 fallback；不要为一次性效果新增机制。

### 6.7 逐行脚本格式（2026-11-12 追加）

参考 `../../NovelWorkFlow/高桥美雪-孤岛篇0.20.json` 的“微信”条目：它每条消息都是一行 `[发送者|类型|内容]`，前端按行解析成微信 UI。本 MOD 采用同样的**逐行类型标签**：`<章节正文>` 内每个非空行都必须以 `[类型|...]` 开头，不再有裸叙述或裸对白。转换层按行解析并剥离标签，不把标签写进游戏正文。

| 行类型 | 格式 | 边界 |
|---|---|---|
| 时间（可选） | `[时间|文本]` | 只写 ActCard 已给的天/时间；不新增时间线。 |
| 对白 | `[角色|对白|文本]` | 每句单独一行；只用角色名（埃莉诺/店主/莉迪亚/母亲索菲娅/警官等），不用“她/他”；文本在第二个 `|` 后。 |
| 表情 | `[角色|表情|key]` | 放在该角色下一句对白前；只对当前可见客户；key 见列表；只在变化时用。 |
| 旁白 | `[旁白|文本]` | 1–3 条/场景；≤40 字；只写动作/环境/道具互动；不写日期/心理/关系总结/设定/系统规则；不是会说话的旁白。 |
| 选择 | `[选择|上下文|主线=N]` + `[选项|...]` + `[/选择]` | 2–3 个 `[选项]`；每个选项不同回应；至少一个改变事实/信息；不用于交易价格。`主线=N` 必填，N 从 1 起，表示块后正文对应第 N 个选项。 |
| 通告 | `[通告|来源|文本]` | 单行；场景内来源；短、具体；不是旁白。 |
| 新闻 | `[新闻|来源|文本]` | 单行；报纸/新闻来源；短、具体；不是旁白。 |
| 文书/Paper Book | `[文书|标题]` + `[文书行|...]` + `[/文书]` | 只在 ActCard 允许时用；每行文书内容带 `[文书行]`；不替代对白；美术/本地化到位。 |
| 自定义 speaker | `[角色|对白|文本]` | 用真实角色名/信息来源；不用旁白。 |
| 行内动作 | 写在 `[对白]` 文本里，用 `<i>...</i>` | 按配额；不得用裸 `*...*`。 |

只做实现、不写行类型的机制：交易（原生交易/ActCard 分支）、原生剧情钩子、结局页/路线 UI、起始天赋、基础肖像/服装。它们由 ActCard/实现处理，不要发明新行类型。

禁止：裸行、裸对白、裸叙述、长舞台动作层（C-D8）、TextAnimator、实时演出、新 UI、语音/自由文本、会说话的旁白（X-D9）。

规则：

- 每个非空行都必须以 `[` 开头；未标记行不合格。
- 标签是元数据，不是正文；转换层剥离；不得出现在最终游戏文本。
- 只允许上表行类型；未知类型/未知 key/缺闭合/字段数不对 → QA 拒绝。
- 对白只用角色名；不得用“她/他”。
- 表情只对当前可见客户；旁白只写动作/环境；选择/通告/文书只在 ActCard 允许时使用。
- 选择块只标选择点，并用 `主线=N` 标出块后主线走第 N 个选项；块后正文只写该选项的回应，其余选项的回应/后果由 ActCard/BranchAppendix/转换层补全，不能做换皮选项。
- 这是现有机制的作者格式，不是新游戏机制；新增行类型走 §8 流程。

示例：

```text
[时间|第23天]
[旁白|门轴响了一声，埃莉诺站在店门外，没有立刻进来。]
[埃莉诺|表情|serious]
[埃莉诺|对白|这个你收吗。]
[店主|对白|按货算。]
[选择|箱子检查后|主线=1]
[选项|报警]
[选项|先找埃莉诺问一句]
[选项|把箱子挪到门外]
[/选择]
[通告|治安部|治安部接警，稍后到店]
[文书|母亲的复核材料]
[文书行|第一页……]
[/文书]
```

### 6.8 无小说空间原则（2026-11-12 追加）

参考书让 AI 写对话体，靠的不是“请写对话”，而是让小说叙述在输出结构里没有位置。逐行脚本要守住同样的边界：

1. 对白优先：角色能说、能做、能展示的，用 `[对白]`；`[旁白]` 是最后手段。
2. `[旁白]` 只写玩家能看见/听见、且没有角色能承载的动作、环境、道具互动；1–3 条/场景；≤40 字；不写日期/心理/关系总结/设定解释/系统规则；不是作者旁白。
3. POV：只写当前在场角色和玩家能感知的事；不写不在场角色、全知信息、别处同时发生的事、别人心里怎么想。
4. 时间：只在场景开始或明显跳时用 `[时间]`；不逐条加；不把日期写进 `[旁白]`。
5. 选择：`[选项]` 是行动/态度/决定，不是让 NPC 解释设定的问题；每个选项要能落地不同回应；不用于交易价格。
6. 对白：必须能直接说出口；太长拆成多条 `[对白]`；不写书面长句/作者总结；符合角色 writing_notes/voice_examples；不用“她/他”做标签。
7. 转换：想写 `[旁白]` 前先问“角色能不能说/做/展示这个信息？”能就改 `[对白]`/`[通告]`/`[文书]`/道具动作；不能才用 `[旁白]`。

反例：

```text
第23天，门轴响了一声，埃莉诺站在店门外，没有立刻进来。
她：“这个你收吗。”
[旁白|她心里明白，自己已经无路可退。]
```

正例：

```text
[时间|第23天]
[旁白|门轴响了一声，埃莉诺站在店门外。]
[埃莉诺|对白|这个你收吗。]
```

- 这些规则不替代已批准机制；它们决定“同一机制写成什么形状”。
- 模板/QA 常驻这些规则；不依赖 world book 自动注入（参考书的 constant 条目是它的常驻机制，我们的对应物是 template + QA）。

## 7. c01–c03 试点适用

### 7.1 默认机制集

- 角色对白：埃莉诺/客户气泡，保留原作 7/9/9 句骨架。原作台词优先；轻改只为止血/衔接，AI 只加互动（选择/动作/表情/通告），不重写埃莉诺的声音。原文见 `docs/原作Eleanor章节_对照稿_2026-11-10.md`。
- 对白：`[角色|对白|文本]`；每句单独一行；只用角色名（埃莉诺/店主/莉迪亚/母亲索菲娅/警官），不用“她/他”。
- 旁白：`[旁白|文本]`，每个来访 1–3 条，每条 ≤40 字；只写动作/环境。

- Act_Outline 每行对应一个游戏章节/来访；ActCard 单独放章节 beat 的事实/选择/分支；正文不得合并、重排或新增章节。

- 任何裸行/裸对白/裸叙述；对白用“她/他”。
- 实时灯光/音效/镜头/角色动画（X-D11）。
- 新 UI、新 3D 场景、新 speaker、新 TextAnimator（C/X）。
- 裸 `*...*` 动作或长旁白（X-D10）。
- 用表情替代台词、给不在场角色换表情、中途换装（A-P2 边界）。
- 为了“电影感”写引擎无法显示的演出。

### 7.3 示例：巡逻灯那一句

批准写法（现有机制）：

```text
[埃莉诺|对白|<i>瞥了一眼门外，把下巴抬高。</i>呵，你们下层区管这种地方叫“商店”啊？]
```

如果这句写成独立场景动作：

```text
[旁白|门外的巡逻灯扫过橱窗，埃莉诺抬眼，下巴抬了起来。]
```

如果巡逻本身需要成为世界事实，用短通告/新闻，或用埃莉诺的一句观察：

```text
[埃莉诺|对白|外面那盏巡逻灯，从刚才就一直照着你的门。]
```

如果试写时认为“灯扫过橱窗”的即时感无法由任何角色台词或通告承载：

1. 不要写旁白替代。
2. 登记 `MECHANISM_REQUEST`，提出 C-D8 独立动作行。
3. 先用 fallback（埃莉诺的 `<i>` 对白 + 一句观察）完成场景。
4. 试点结束后再决定是否开发 C-D8。

### 7.4 试点验收

- 机制声明齐全，无未批准机制。
- 新增裸 `*...*` = 0。
- `<i>` 配额、动作拍、选择密度达标。
- 表情边界正确；无中途换装；无非在场角色表情。
- 没有旁白说话、长动作、实时演出。
- 每个来访至少一个事实/信息变化。
- 盲评：新版 vs 现版，用户和 1–2 个玩家更想继续玩新版。
- 试点目标是验证“现有机制能否让原作场景变得可玩”，不是证明新机制。

## 8. 新机制开发流程

任何 C 条目要进入 A，必须完成：

1. **一页 spec**：目的、玩家体验、UI/交互、适用范围、禁止用法、技术风险、兼容/旧档、测试计划、回退。
2. **垂直切片**：选一个真实场景实现；实机测试；截图/日志；如有代码，跑 `check_project.py`、`dotnet build -c Release` 和必要的扫描。
3. **用户批准**：明确同意新增，并确认边界。
4. **更新契约**：把条目从 C 移到 A，写清 allowed/forbidden；更新版本和变更记录。
5. **更新入口**：在 `CLAUDE.md`/README/docs 索引中链接本文件；涉及路线/结局时同步 `docs/route_map.html`、`site/index.html` 和维护文档。
6. **之后才能写内容**：未完成上述步骤前，正文不得使用该机制。

禁止“先写再补机制”“临时旁白替代”“用代码补丁偷偷加演出”。机制新增必须显式、可审查、可回退。
