# 文本 AI 味定点修订执行计划

**日期：** 2026-11-17  
**状态：** 待执行  
**适用范围：** 当前正式正文、NovelWorkFlow_Eleanor、Super QA 及候选补丁流程

## 1. 计划结论

五场对照和最近两次整场候选已经足够说明：继续让主笔重新规划一整场，会带来新增章节、选择、分支和事实越权。接下来的优化改为**定点编辑**：保留当前正式正文的结构，只修改已经定位的少量台词或动作，让每句话承担当场的行动、态度或关系变化。

本计划不再进行模型横向测试，不再生成整场 Opus/Gemini 候选，也不修改正式模板。首批只处理 `c19`，确认流程可控后再处理 `c10`。

## 2. 固定边界

以下内容在本计划中冻结：

- 客户端数量、场景键、block/index、speaker、expr、顺序和旧档入口；
- 选择数量、选项文字、分支结果、路线、结局、状态和交易事实；
- 窗口内外空间关系、可见角色、公共尾段和闭店/次日衔接；
- 已由作者确认的告白句、镜像句、终章句和关键回扣；
- `writer_prompt_template.md`、`writer_system_prompt.md`、正式 world book 和 `Content/`，直到采用闸门通过。

本计划允许的变化只有：在明确授权的现有 block/index 内，对 text 做少量 1:1 改写、删除重复解释或把总结句换成当场反应。Agent 不直接写入正式正文；实质性台词变化必须来自 Super QA 候选并保留逐行来源。

## 3. AI 味的具体处理目标

每个修改点必须对应一个可指出的问题：

1. **重复解释：** 同一事实已经通过物件、交易或对白成立，后文又完整复述。
2. **总结腔：** 角色替读者解释“这意味着什么”“从此以后如何”，但没有新增行动或压力。
3. **长连续：** 同一 NPC 连续说话，且中间没有新的信息、玩家回应或可见动作。
4. **角色同声：** 不同角色用同样完整、平滑、礼貌的句式完成相同功能。
5. **玩家空泛：** 玩家回应只剩“嗯/好/行”，没有边界、判断、承担或照顾。
6. **流程泄漏：** 正文出现后台配置、错误交易值、标签说明或模型式解释。

不把“更口语”“更像人”“更短”单独作为修改目标。角色的骄傲、停顿、重复和性格化口头习惯可以保留，只处理它们在当前段落中失去功能的情况。

## 4. 首批场景顺序

### 4.1 第一场：`c19`

`c19` 是首个修订对象，因为问题集中在告白后的解释堆叠，且没有交易契约和公共交易尾段风险。

必须保留：

- 埃莉诺主动告白；
- “喜欢”与“报恩”之间的界线；
- 吊坠、母亲已安全、拾荒/卖货和价格历史的有效回扣；
- 玩家接受或只做朋友的两个选项；
- 接受与朋友两条既有后续，以及次日/后续入口。

优先审阅：

- `c19.b101` 与 `c19.b101_return` 中重复解释来访原因、母亲和报恩边界的句子；
- 告白前后连续确认关系的句子；
- `c19.b102`、`c19.b103` 中已经由玩家选项表达、又被重复说明的收尾句。

禁止：

- 修改锁定告白句的语义；
- 新增或删除选择；
- 把一场拆成两场；
- 新增当晚事件、债务、电子元件状态或线材承诺；
- 改动镜像段的对应关系。

### 4.2 第二场：`c10`

只有 `c19` 形成可接受的定点修订后才处理 `c10`。`c10` 的主要问题是整体过长，不能用几句润色解决，因此本轮不做全场压缩。

优先审阅：

- 埃莉诺询问莉迪亚时重复交代“来过/住址/盒子”的句子；
- 掮客报价段中重复说明手镯风险和所有权的句子；
- 莉迪亚拿回手镯时重复解释家族压力和欠情的句子。

必须保留：

- 三次既有来访的运行顺序；
- 埃莉诺保护手镯和住址的主动性；
- 掮客的报价与既有交易结果；
- 莉迪亚的家族压力、手镯归属和现有选择回应；
- `c10.n213` 公共尾段只接入一次。

如果必须改变章节数量、选择结构或 block 关系才能改善节奏，停止该场并记录为结构问题，不在本计划中处理。

## 5. 执行步骤

### P0：冻结当前基准

为目标场景保存：

- 当前 Content 源文件哈希；
- 当前中文、英文键和值哈希；
- 当前场景路径、block/index、speaker、expr 和选择映射；
- 现有文本的连续对白、旁白和重复解释清单；
- 正式模板、system prompt 和 world book 哈希。

产物目录：

```text
tools/NovelWorkFlow_Eleanor_Test/Test_Output/POINT_EDIT_2026-11-17/
├─ baseline/
├─ c19/
└─ c10/
```

P0 完成后不得覆盖 baseline。

### P1：编写逐行 Brief

每个 Brief 必须先落盘，未落盘不得调用 QA。格式固定为：

```text
场景：c19
父稿：Content/... 的当前正式源
任务模式：existing_scene_point_edit
允许修改：c19.b101:3、c19.b101:4
必须原样保留：锁定告白句、选择、表情、镜像句、结果块
问题：重复解释母亲安全与报恩边界
目标：保留信息，但让其中一句承担当场动作或关系压力
禁止：新增事实、删除事实、改变 block/index/speaker/expr/顺序
验收：只出现允许行的 text 差异；其余字段逐项相同
```

每个场景首轮最多列 3 个修改点，每个修改点最多覆盖 2 个相邻文本行。禁止以“整段润色”“整体自然化”作为允许范围。

### P2：离线检查 Brief

Agent 在调用前检查：

- 每个 block/index 存在于当前正式源；
- 允许修改行属于同一场景和同一运行路径；
- 锁定行没有进入允许列表；
- 选择、交易、状态、公共尾段和镜像行均列入冻结项；
- 修改目标是文本问题，而不是结构问题；
- Brief 只引用当前正式源，不引用被拒绝的整场候选作为父稿。

检查失败时只修 Brief，不调用模型。

### P3：一次 Super QA 局部修订

每场最多一次 Super QA 请求，父稿必须明确指向当前正式稿，不能指向上一轮被拒绝的整场 Opus 候选。

Super QA 输出必须是可解析的逐行结果，至少包含：

- 场景、block/index、speaker、expr 和原顺序；
- 原文与候选文本；
- 修改理由；
- 未授权字段是否全部保持不变；
- `zero_changes` 或候选状态。

Super QA 不得：

- 输出新的 `[章]` 或完整章节；
- 新增、删除、重排选择或分支；
- 改动交易、预算、客户、状态、路线或结局；
- 擅自复制或替换表情；
- 把多个修改点扩展成整场 voice pass。

### P4：逐行合同检查

候选必须同时通过：

1. 允许行之外的 text 完全相同；
2. block/index、speaker、expr、顺序和行数完全相同；
3. 选择、交易、状态、路线、公共尾段和入口完全相同；
4. 不出现后台词、占位符、结构标签或新事实；
5. 原有路径仍能完整展开；
6. 候选没有把恋爱吸引力、阶级反差、角色主动性或玩家回应删掉。

任何一项失败，结果为 `retain_A`，不继续 QA，不生成 patch。

### P5：局部冷读和采用判断

只比较修改行及其上下各两行，避免把整场体量重新变成测试对象。逐项回答：

- 这句是否仍像该角色在此刻会说的话；
- 修改是否减少了重复解释；
- 是否出现了更具体的动作、压力或回应；
- 玩家和 NPC 的来回是否更清楚；
- 是否保留了原有爽点和情感回报。

采用要求：至少两个问题有明确改善，且没有事实、结构或声音回归。否则记录 `retain_A`。

### P6：生成未应用 patch

只有 `adopt_C` 才生成逐行 patch。patch manifest 至少记录：

- 源文件和旧哈希；
- block/index；
- 原文本和新文本；
- Brief 哈希；
- Super QA 候选哈希；
- 采用理由和回退位置。

patch 只保存为未应用审阅文件，未经作者最终批准不写入 `Content/`。

### P7：获批后的正式接入

获得批准后才执行：

1. 应用 patch 到内容源；
2. 运行 `python tools/build_content.py`；
3. 运行 `python tools/check_project.py`、`python tools/check_route_map.py` 和文本合同检查；
4. 核对中文/英文键、选择、入口和受影响路径；
5. 编译 Release；
6. 对 `c19` 或 `c10` 做一次实际运行验证；
7. 保存构建、路径和回退证据。

任何验证失败都回退该 patch，不扩大到下一场。

## 6. 采用标准

候选必须满足全部硬条件：

- 只改 Brief 允许的行；
- 不改变结构和运行事实；
- 不新增后台语言或流程泄漏；
- 角色声音仍然可辨；
- 恋爱吸引力、阶级反差和玩家爽感没有减弱；
- 能指出至少两项具体的局部收益。

以下情况直接保留现稿：

- 只是句子更短；
- 只是把角色改得更礼貌或更平滑；
- 删除了情绪、主动性或暧昧张力；
- 修改理由只能写成“更自然”；
- QA 为了修一行而重写整段。

## 7. 责任和调用上限

| 工作 | 责任 | 上限 |
|---|---|---:|
| 基线、路径和 Brief | Agent | 不调用模型 |
| 局部文本候选 | Super QA | 每场 1 次 |
| 候选合同和逐行比较 | Agent | 不调用模型 |
| 最终采用决定 | 作者/Agent | 每场 1 次 |
| Gemini 或整场 Opus | 本计划不安排 | 0 次 |

首批最多 2 次 Super QA 调用：`c19` 1 次、`c10` 1 次。第一场失败或没有净收益时，不自动进入第二场。

## 8. 完成定义

本计划完成并不要求文本一定发生变化。满足以下条件即可结束：

- `c19` 有完整 baseline、Brief、QA 结果、合同结果和采用/保留决定；
- 若 `c19` 采用，再按同一流程处理 `c10`；
- 所有候选都有父稿哈希和逐行差异；
- 没有正式正文、模板、路线或 system prompt 的未授权变化；
- 失败时保留证据，不追加模型调用；
- 若有 patch，完成作者批准后的构建和运行验证；若无 patch，明确记录 `retain_A`。

当前第一步：只冻结 `c19` 基线并编写 `c19` 定点 Brief；在 Brief 通过离线检查前，不调用任何模型。
