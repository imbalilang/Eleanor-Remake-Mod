## 一、审阅结论

本提案的方向是对的：它试图把“现有场景修订”、结构研究、ActCard 体量和交易事实从主笔的自由判断中分离出来。它也准确回应了 R2 暴露的两个硬问题：`love_a2_01` 的预算被主笔误读，以及公共尾段被不同候选重复或错放。

但提案目前**不应原样批准或应用**。原因不是文风方向错误，而是几处协议仍然互相冲突：任务模式没有对应的确定性输出协议；长度字段没有稳定 schema；现有场景的“不得拆客户端”与模板原有“超硬上限必须拆章”并存；交易示例仍可能诱导模型输出占位符；配套说明声称的公共尾段映射没有在 diff 中完整落地。

因此本轮决定为：

- `template_proposal.diff`：**退回最小修订，不应用**；
- 正式 `writer_prompt_template.md`：**保持不变**；
- `writer_system_prompt.md`、正式 world book、`Content/`：**保持不变**；
- `love_a2_01`：继续停在 `blocked-template-approval`，不发送新的付费主笔请求；
- `v2_r1c1`：继续停在结构研究闸门，不生成正文；
- 下一步先修订提案和场景输入契约，再进行单场 R2 对照。

本批注只审阅规则和执行顺序，不批准模板改动，也不把候选文本写回正文。

## 三、逐条批注

### P1-1：任务模式与正式输出协议冲突

**定位：** diff 第 7–8 行，`Authors_Note 1`；配套说明第 1 项。

新增规则同时要求“现有场景修订”和“结构研究只输出结构报告”，但正式输出协议仍规定主笔只能输出 `<思维草稿>`、`<章节正文>`、`<分支附录>`，并要求每个非空正文行带脚本标签。没有独立的“结构报告”格式，主笔可能把结构方案放进正文，或者输出无法被 `parse_tagged` 接受的自由文本。

**处理决定：**

1. 结构研究不调用 writer；由 Agent 在离线研究文件中输出 `structure_report`，至少包含 line map、key remap、路线图影响、风险和 `generate=false`。
2. 正式模板只增加“现有场景修订”模式所需的约束；删除“结构研究由主笔输出报告”的表述，或改为“本模式不调用 writer”。
3. 在 ActCard/运行契约中把 `task_mode` 设为枚举：`existing_scene_revision`、`new_creation`；结构研究作为管线外任务，不作为 writer 模式。

**验收：** 同一个输入不能同时产生结构报告和章节正文；`task_mode=existing_scene_revision` 时客户端数量、选择、路线、结局和交易事实均为冻结输入。

### P1-2：ActCard 长度字段没有确定性结构

**定位：** diff 第 15–16 行，`Authors_Note 8`。

提案要求模型读取“目标、关键段、最长 NPC 连续和硬上限”，但当前 ActCard 主要是自然语言。仅在提示词中写“读取【长度】”不能保证模型正确解析，也不能让 contract checker 复现同一结果。

**处理决定：**

1. 在隔离 world book 的 `pilot_inputs` 或场景 contract 增加结构化 `length_budget`，至少包含 `target_min`、`target_max`、`soft_max`、`hard_max`、`key_segment_max`、`max_npc_consecutive`、`dialogue_ratio_min`、`narration_ratio_max`。
2. ActCard 的自然语言【长度】继续保留给主笔阅读，但不作为唯一来源。
3. 准备阶段校验字段完整性和数值关系；缺字段时拒绝准备，不让模型自行补默认值。
4. contract checker 与主笔输入使用同一份已解析预算，并记录预算哈希。

**验收：** 任何一条路径的行数、对白比例、最长 NPC 连续和关键段长度都能由 checker 按同一预算重算；模型不能通过改写“目标长度”规避检查。

### P1-3：长度统计口径需要写成机器规则

**定位：** diff 第 15–16 行。

“`[角色|表情]` 计入正文行”与“表情标签不计气泡”可以同时成立，但提案没有定义正文行、对白气泡、表情标签、旁白行和选择元数据的边界。若不明确，A/B 候选会出现人工统计与 checker 统计不一致。

**处理决定：** 在场景 contract 中固定以下口径：

- 正文行：`<章节正文>` 中的非空脚本行；`[章]`、`[选择]`、`[选项]` 及其元数据不计入；
- 对白气泡：`[角色|对白|...]`、`[SEC|对白|...]` 各计一条；
- 表情标签：`[角色|表情|...]` 计正文行，但不计对白气泡；
- 旁白行：`[旁白|...]` 计正文行，并计入旁白比例；
- 互斥选项和交易结果不相加，按单条可达路径统计；公共尾段按运行映射只计一次；
- 交易声明、交易结果块和分支附录不混入章节正文行数。

**验收：** checker 输出每条路径的正文行、气泡数、旁白数、最长 NPC 连续、公共尾段次数，并能定位到具体行。

### P1-4：现有场景修订的拆章规则仍然冲突

**定位：** diff 第 16 行，以及正式模板 `Script_Format` 第 90 行的既有规则。

提案新增“超过 ActCard 预算先报告信息负担与可分离段，不擅自新增客户端”，但保留了“超过硬上限必须拆成新的客户端来访”。现有场景修订不能改变客户端数量；新创作模式才可以在授权范围内断章。两条规则同时存在时，主笔没有可靠的优先级。

**处理决定：** 明确模式分流：

- `existing_scene_revision`：既有客户端数量、场景键、入口、选择、交易、尾段和路线影响冻结；超预算只输出离线 `over_budget_report`，不改正文结构；
- `new_creation`：保留原有拆章规则，但仍须受 ActCard 和路线图约束；
- 规则优先级写明为：运行契约冻结项 > ActCard 结构字段 > 模板默认值；
- 主笔不得自行把“可分离段”变成新 `[章]`。

**验收：** 现有场景候选的章节键和客户端数量与父稿完全一致；超预算时准备流程生成报告并阻止候选进入 QA，而不是自动改键。

### P1-5：交易占位符可能被原样输出

**定位：** diff 第 24–25 行和第 33–37 行。

示例中的 `预算=<契约值>`、`客户=<契约值>`对人类是说明，对模型可能是可复制的输出。正式解析器和 contract validator 无法把它当作具体交易事实；“按代码配置”也已经在 Opus 候选中出现过。

**处理决定：**

1. 模板说明中不得放一个看起来像合法脚本行的占位符示例；改为文字说明“此处必须填入运行契约的具体值”。
2. 现有场景修订的运行输入直接注入已解析的具体交易声明，至少包括 `intent`、`type`、`budget`、`customer`、`result_map`、`anchor_id`。
3. 增加确定性拒绝词检查：`<契约值>`、`按代码配置`、`按运行契约`、`待定`、`未知`不得出现在交易声明中。
4. 缺少值时在准备阶段失败；主笔不得补值、猜值或把交易改成第二笔交易。

**验收：** `love_a2_01` 只能产出 `预算=150`、`客户=索菲娅`、`BUY`、`HOUSEHOLD_GOOD`；任何其他值在付费请求前被拒绝。

### P1-6：公共尾段的配套承诺没有在 diff 中完整实现

**定位：** `template_proposal.md` 建议变更第 4 项；diff 没有对应完整的输出、入口、执行次数和结果映射协议。

配套说明声称支持公共尾段 block、入口和执行次数，并要求主笔只写结果独有反应；但模板没有定义公共段的输入字段、主笔可见范围、结果块与公共段的连接方式，也没有说明谁负责验证“恰好一次”。如果继续这样，模型可能把 `la2_s1_common` 复制进四个结果块，或把公共段放回正文。

**处理决定：**

1. 把公共尾段定义为运行契约字段：`block_id`、`entry_key`、`execute_once=true`、`result_keys`、`after_trade`。
2. 主笔只输出每个结果独有的反应；公共段不进入候选重写范围，不在每个结果块复制。
3. 由 contract checker 检查四个结果均指向同一公共段，且每条可达路径执行一次；主笔不自行改入口或次数。
4. 如果本轮不准备实现上述字段，应从 `template_proposal.md` 删除“已支持公共尾段”的表述，不把未实现能力列为提案目标。

**验收：** `love_a2_01` 的四条交易结果都能到达 `la2_s1_common`，每条路径只接入一次，并继续调用 `LoveA2Closing.FinishFromVisit`。

### P2-1：模板修改范围应保持最小

**定位：** 整个 diff 与配套说明。

提案目前没有直接扩写“反 AI”文风条款，这是正确的；后续修订也不应继续堆叠“更自然”“更像人”等不可检验要求。五场报告表明，长连续对白和结构拥挤同时出现在 Opus 与 Gemini 中，单靠模型或泛化文风提示不能解决。

**处理决定：** 本次正式模板只处理协议冲突：模式、结构化预算、交易事实和公共尾段映射。具体文风继续由 ActCard 的场景事实、主笔候选、Super QA 定点 Brief、A/B/C 冷读负责。

**验收：** 修订 diff 不新增路线、结局、状态、道具、客户、预算、选择或新表现形式；不把“减少 AI 味”写成新的自由创作授权。

### P2-2：交易结果词汇存在既有命名不一致，需在应用前统一

**定位：** diff 第 14、26、36–38 行与正式模板 `Trade_Contract` 第 146 行。

当前同时出现“让利/高价/压价/未成交”“溢价”“无成交”等不同命名。名称只要与代码映射不一致，文本可能合格但运行挂接失败。

**处理决定：** 以现有 contract validator 和代码中的结果枚举为唯一来源，在修订提案中给出中英文/内部键的单一映射表；模板只使用已批准的显示词，不能临时创造同义词。

**验收：** 四结果、无成交和公共尾段的显示词、内部键、挂接函数在同一份测试 fixture 中逐一对应。

## 四、必须修改、建议修改与暂不处理

### 必须修改后才能请求批准

1. 将 `task_mode` 从自然语言说明改成运行契约枚举；结构研究移出 writer。
2. 增加结构化 `length_budget`，并固定统计口径。
3. 明确现有场景修订不可拆章，新创作才可按原规则拆章。
4. 删除可被复制的交易占位符示例，改为具体值注入和缺值拒绝。
5. 补齐公共尾段的运行契约和单次接入检查，或删掉配套说明中的支持承诺。
6. 统一交易结果显示词和内部键映射。

### 可以随本轮保留

- 保持 Opus 为生产默认，Gemini 仅作为平行候选；本提案不借机切换默认模型。
- 保留“交易事实不由主笔猜测”的方向。
- 保留“ActCard 预算优先于模板默认值”的方向，但把预算放入结构化输入。
- 保留公共尾段不复制到每个交易结果的目标。

### 本轮不处理

- 不在模板中加入更多泛化的“人类文笔”或反 AI 词表。
- 不重写正式 `writer_system_prompt.md`。
- 不修改正式 world book、`Content/`、路线图、客户端数量或结局。
- 不为 C19、DV08、C17 或 `v2_r1c1` 发起新的付费正文生成。

## 五、批准后的执行闸门

以下步骤按顺序执行；任一步失败就停在该闸门，不发送下一次付费请求。

### G0：提案修订与离线审阅

**产物：** 修订后的 `template_proposal.diff`、`template_proposal.md`、字段映射说明和变更清单。

**检查：** `git apply --check`；静态搜索旧的 `预算=200` 通用示例、`<契约值>`、`按代码配置`、结构研究 writer 模式和拆章冲突句。

**通过条件：** 以上五项均已消除或明确限定在历史示例；没有修改正式模板。

### G1：作者批准正式模板修改

这是唯一需要作者明确批准的闸门。批准对象必须是可审阅的最小 diff，不是“同意继续试试”。批准前不修改 `writer_prompt_template.md`，也不发送模型请求。

### G2：应用并建立输入基线

1. 记录正式模板旧 SHA-256。
2. 应用最小 diff。
3. 重新生成 R2 输入和每个场景的 manifest/hash。
4. 运行 `python tools/NovelWorkFlow_Eleanor/check_worldbooks.py`、`python tools/test_novel_workflow_r2.py` 和三份场景 contract 检查。
5. 确认 `writer_system_prompt.md`、正式 world book、`Content/` 没有非目标变化。

若 G2 失败，恢复模板变更并保留失败证据；不得进入模型调用。

### G3：单场有界生成

只运行 `love_a2_01`，使用相同的已解析事实契约和长度预算：

- Opus 1 次；
- Gemini 1 次，作为平行对照；
- 串行、无自动重试、无 fallback；
- 不重跑 C17、C19、DV08；
- `v2_r1c1` 继续只做结构研究。

生成前必须记录请求体大小、输入哈希、模型 ID 和预算哈希；请求体目标不超过 16 MB，硬上限不超过 20 MB。

### G4：候选合同与文本审读

先检查 B 候选，检查顺序固定为：

1. XML/标签完整性；
2. 客户端数量、场景键和入口冻结；
3. `BUY / HOUSEHOLD_GOOD / 预算150 / 客户索菲娅`；
4. 三个回应、四个交易结果、公共尾段一次接入；
5. 单路径长度、对白比例、最长 NPC 连续；
6. 角色声音、玩家回应、阶级反差和恋爱吸引力是否有相对 A 的明确净收益。

任何预算、选择、物件、客户、状态、公共段次数或路线事实错误，直接 `retain_A`，不让 Super QA 修复结构事实。

### G5：定点 Super QA

只有 B 通过 G4，才创建以 B 为父稿的 Brief。Brief 必须写明允许改动的行、禁止改动的字段和验收条件；最多一次请求。

- QA 只做最小、可追溯、逐行修订；
- 不得修复预算、交易类型、章节键、公共尾段映射或路线结构；
- 没有明确净收益时记录 `zero_changes`，不继续消耗调用。

### G6：采用或保留 A

只有候选同时满足以下条件才生成未应用 patch：

- 所有 G4 合同检查通过；
- 相对 A 在角色声音、玩家爽感、阶级反差或恋爱吸引力上有可指出的净收益；
- 没有新增路线、结局、状态、道具、客户、预算、选择或 UI；
- 中英文键、交易挂接和公共尾段检查通过。

没有净收益时保留 A，记录比较结论，停止本轮调用，不生成 patch。
