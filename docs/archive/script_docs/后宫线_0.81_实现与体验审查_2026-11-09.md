## 结论

设计方向可以保留；当前实现不能视为完成验收的最终版本。剧情主体、美术和经营对象已经接入，但状态流、原主线接管、旧档入口及口碑收益仍有明确缺口。建议先完成一次稳定性修订，再进行新档和旧档完整实机验收。

判断以代码可证事实为主；涉及原生顾客调度频率、成交回调/存档重建和价格收益的部分，仍需实际游戏验证。

## 阻断与高优先级问题

### 1. 暂缓表白没有对应的再确认出口

证据：src/DualStory.cs:144、217；src/DualDirector.cs:119、191、209。

dr05 暂缓只 CompleteScene，没有设置原系统的 Romance=2；dr08 只有工作对白及 WorkState 提交，没有恋人/朋友选择。随后 dr09 等待 RomanceConfirmed，而原23章的再确认被 SuppressMainChapter 压住；ReconcileMainProgression 又可能直接跳到24章。即便其他原章偶然提供一次告白，也不等于实现了设计规定的暂缓恢复路径。

dr06 仍在 dr08 前必播，也没有在暂缓时延后约饭。dr05 朋友分支写 Romance=4，而原状态定义 3 是朋友、4 是锁定，应统一语义。

修订：明确提交暂缓状态；让工作场景先行，在 dr08 复用原再确认及赠礼逻辑，确认后补约饭/撮合反馈，朋友分支正常返回朋友结果。为暂缓和不满足表白资格分别建立自动路径测试。

### 2. 原主线与双恋没有完成可靠的接管和事实提交

证据：src/DualStory.cs:144、260；src/DualDirector.cs:148、191；src/StoryDirector.cs:105。

dr05 成功仅写 Romance=1 和场景完成，没有推进原20章，也没有清 PendingScene。后者可能由 RecoverPending 恢复，但不应把正常完成当作中断恢复。SuppressMainChapter 只压22～24，原20章仍可能重播告白。

dr11 把 Chapter>=21 当成原合作已完成；但 Chapter=21 表示21章待播。它可以直接 CompleteCore，把尚未发生的合作介绍和买家跳过。OriginalCooperationDone 字段没有实际提交/判定用途。

修订：明确逐场接管边界，分开记录告白、工作、合作介绍、合作买家及原核心奖励事实。核心收束读取实际完成标志，不读“已到达某章”。

### 3. 旧恋人档缺少铭牌领取路径，且仍可能回放旧事实

证据：src/DualMigration.cs:11；src/DualStory.cs:62、431；src/DualDirector.cs:225。

旧档入口 accepted 没有接 BuildEntrySecondHalf 或 GivePlaque，却在完成时把 dr02 标记完成。后续补领要求 PlaqueRetryDay>=0，旧档该字段默认 -1，因此正常接受旧档入口不能取得铭牌。

迁移在玩家确认入口前就 Accept(2)，导致“符合资格”和“接受扩展”混为一谈，可能提前抑制原后日谈。dr08 也没有根据已有 WorkState 跳过重新找工作的叙述；旧档专用 dr_legacy_ch7 文本未接入。

修订：迁移只标资格；接受后走独立、可恢复的铭牌领取节点。保留既有工作和礼物事实，旧档使用专门的撮合反馈。

### 4. 同日剧情门禁阻断了计划中的并行经营

证据：src/StoryDirector.cs:105、111、114；src/DualDirector.cs:90。

重要剧情排队时写 LastQueuedDay；外层下一次检查同日即返回，抵达不了 DualBusiness.TryQueue。新档连续每日推进感情剧情时，短经营客无法按计划同日独立排入，经营反馈容易一直落到“没有成交”。

反方向上，业务排队先于原主线；业务繁忙也可能推迟尚未完成的原章。现有逻辑没有实现“重要剧情每天一次、短经营客每天一次”的两套配额。

修订：分别设置剧情和经营配额，原合作买家与新买家共用短客配额，保留紧急事件优先级。先用调度测试验证，再确认实机一日内的顾客生成时机。

### 5. 口碑收益条件与反馈不一致

证据：src/DualBusiness.cs:137、245、252；src/DualStory.cs:455。

ReferralChance 只检查 DualState.Confirmed：确认双恋即75%，没有要求两笔成交或反馈。完成两笔业务但未确认关系仍是50%，通知却说客人增加。

CompleteBusinessVisit 直接清 FeedbackPending 并置 FeedbackShown，正常经营收束会让专门的 reputation 场景失去排队资格。

修订：两笔不同业务真实成交后进入待反馈，反馈提交经营升级。关系状态只控制约定的路线收益归属，不代替经营成就。通知和实际概率同步生效。

### 6. 业务预约、补做和明示要求尚未闭环

证据：src/DualBusiness.cs:82、229、280；src/DualStory.cs:192、232；Content/dual_romance_v04.json 的 dr07_business、dr09_business_none。

- 第二业务只有 dr07 调用 ArrangeSecondBusiness。拒绝或未成交后无补约入口；计划中的一次性供货未实现。
- 预算600、最低耐久150只在买家到店时明确，预约对白没有显示具体数值。
- QueueBuyer 后预约仍为1，只把 BusinessDueDay=-1；若成交/未成交收束尚未发生而原客不再在队列，存在重复排预约的风险，需测跨日和中断。
- 首笔教学、第二预约在随机引荐冷却检查之前返回，未统一受 D+2 限流约束；两个业务共用 BusinessDueDay，缺少各自的到期和恢复事实。
- dr09 对所有“尚未成交”都说买家已在别处找到，包含尚未到店/未预约的情况。
- IsFirstItem 接受 HOUSEHOLD_GOOD，但原生购买标签只列奢侈品/艺术品/高档品。需要统一真实筛选与界面接受范围，避免普通家居用品也算精品。

修订：给预约独立身份、状态和日期；到访与完成分别提交；增加短对白补约，已结束需求由另一位通用客接替；所有买家统一限流。接单前明示预算与耐久，备货和拒绝均不影响恋爱。

### 7. 文本块引用错误使新人设和补领对白静默缺失

证据：src/EleanorStory.cs:734、735、750、751、781；src/DualStory.cs:75、439、444、450；src/DualText.cs:16。

确认不存在的引用共10个：common09_arrival、common09_added、common09_high_price、common09_after、common10_family、legacy_entry_open、legacy_entry_notice、dr_plaque_pickup、dr_plaque_removed、dr_plaque_no_stock。

其中共同补充真实块名带 common09_add_/common10_add_；common09_added 还调用了读取原主线表的 StoryEngine.Append。结果不是“已经同步新人设”，而是记录错误后略过相关对白。旧档两项缺块当前有后续有效正文替代，主要表现为错误日志；不能把所有缺块都说成整场消失。

dr_common_sync_* 共同替换块虽然已经生成，但未见运行调用。应逐项落实适用分支或明确取消，而非仅统计为已完成内容。

修订：核对表名和块ID，把双恋静态引用、动态日常ID、选项键及所有条件分支纳入检查。

## 其他需要在稳定版前处理的问题

1. **铭牌补领会被延后到永远**：AppendPlaqueFollowup 每次发现缺失先 MarkPlaqueLost，把重试日设为今天+1，随后立即检查补领，自然不满足。只在首次确认丢失时设时间。PlaqueExists 捕获错误后返回 false，也不能被直接当作“已证明遗失”。补领目前只附在 dr04/dr09，后期缺失还需要一个低频、可达的恢复入口。
2. **原奖励没有完整复用**：dr08 未接原吊坠领取/拒绝/已售分支；dr11 直接给香水并 CompleteCore，未接原结尾的乙线回执提交。赠香水失败后也仍完成该场，缺少此路径的补领。应复用完整事实提交，而非仅复制奖励调用。
3. **拾荒资格未分流**：CompleteCore 仍给普通恋人 ScavAssist，ScavAssistance.Eligible 不检查双恋，确认时没有迁移未来资格。结果可能同时享有原拾荒和新铭牌收益，与剧本排除终局增益叠加的规定不符。
4. **dr03是假定售货已完成的纯对话**：使用 DIALOGUE 顾客，没有货物生成或成交回调，却开口说物品换不了多少钱。应接真实原售货收束，或改为不声称发生交易的来访。
5. **时间/美术事实变体未完成**：部分场景记录日期，但文本没有按日期切换；两种约会画像共享“披肩搭臂弯”描述。需要依实际间隔和画风选正文。
6. **未来schema保护不闭合**：OnLoaded 对未来版本返回，但 CanOfferEntry/CanOpenFromFacts 未统一排除未来schema；Entry=0 时仍可能接受入口并覆盖版本。未知状态必须停写。
7. **调试重置不可靠**：DualState.Reset 先把 scene_count 清零再读，循环不执行；Complete 也不维护该索引。scene.*、scene_day.* 等历史残留会污染F9测试。应基于明确键集清理，并验证重置后状态。

## 设计、经营和互动体验的判断

### 建议保留

莉迪亚通过荐店认识玩家的处事方式，帮埃莉诺追求玩家后自己动心，这条因果成立。经营业务应让她对玩家产生新的认识，而不是变成靠钱购买三人关系。

埃莉诺凭实际工作重新进入上层区，莉迪亚提供熟人介绍和生活协助，能保留埃莉诺自主性，也与侍从线“大额投入、主人身份反差”区别开。dr18莉迪亚约会、dr19埃莉诺独处、dr20共同晚饭的顺序应保留。

使用原柜台、橱窗、顾客和交易界面符合轻量MOD目标，不需要为此新增地图、手机、日程表或好感面板。

### 建议调整

- 当前入口说明是“只接受撮合，不代表接受双恋”，但后续已改为无退出的固定方向。不要简单恢复每章退出菜单；应选择一个真正的分流点，让入口清楚选择后宫扩展，或在莉迪亚明确告白时才进行唯一双恋选择。不能让玩家只想接受追求埃莉诺的帮助，却必然被导入后宫。
- 让经营任务与感情并行。缺货、未摆牌、接单失败可以改变一两句回应，但不能拦住约会。奖励概率由经营成绩决定，不由恋爱确认代替。
- 50%/75%只能作为首轮参数。现有预算500/600不等于净收益；需记录采购成本、实际成交价、每日顾客占用、原订单挤占，再判断相对其他路线是否过强。
- 亲密互动优先嵌入已有场景：成交后留下聊天、看到新发夹、约会像切换、三人晚饭留下第三份点心。无需为了增加按钮另外制造事故和任务。
- 三人明确同意应保留，但连续讨论可以减少重复承诺，多用埃莉诺提出具体相处要求、莉迪亚真正留下来、玩家记得两人不同喜好来展示关系成立。
- 七组日常四日一次需要28日才轮换一遍。对接近75天结束的普通流程，它主要是长局余韵，不能用来证明主剧情已经提供足量互动。
