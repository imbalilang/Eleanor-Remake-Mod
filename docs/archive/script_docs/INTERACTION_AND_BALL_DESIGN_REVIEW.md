# 《互动补强与上层区晚会》第二稿审查

> 实施追记（2026-11-09）：本文保留第二稿的历史审查结论；以下“未修改/未生成”描述的是审查时点。现已修订第三稿并随0.75发布，见 `INTERACTION_AND_BALL_DESIGN.md`、`INTERACTION_AND_BALL_IMPLEMENTATION.md` 与 `RELEASE_0.75.md`。按用户后续要求，D改为普通对话和旁白，不再实施本审查讨论的关店/跨夜原型；原版复用上层区形象，只为《少女当铺》新增晚礼服。六项主要发现均已处理，实机验收仍由用户进行。

日期：2026-11-09。审查对象：`INTERACTION_AND_BALL_DESIGN.md`第二稿；对照当前运行源码、内容JSON及本机0.46D原版代码。没有修改设计正文或运行逻辑，没有生成立绘，也没有发布。本次是静态设计与代码对照审查，不代表已经完成新功能原型或实机验证。

## 结论

**创作方向成立，可进入分项开发和技术原型；尚不能作为不需补充决策的完整执行规格直接实施。**

- A/C体量受控，复用现有来访和估价，不增加新的经济门槛；修正下述结果分支与接入位置后即可开发。
- B晨间入口可原型，但当前前置条件与现有状态提交顺序形成循环，必须先改。
- D作为第28章后的公开恋爱后日谈有成立的动机；最后访客方案可尝试，但外出成本、夜间恢复和预约冲突规则尚未封闭。应以原型验收为门槛，再确定正式文本与美术交付。

## 主要发现

### P1-1：B要求一个由本章结束才产生的状态

设计第130行要求“母亲安全已由现有救母流程确认，第16章尚未播放”。当前阅读第16章对应`MaidStory.CreateReunion`，`MotherState=1`和研究盘结果是在本章末尾的`FinishMain`回调中提交，之前没有独立的母亲获救确认事件。`VanillaEleanorBridge`处理的是埃莉诺本人被捕／获释，不是母亲安全。

若把该前置直译成`MaidState.SafeMother`或`MotherState==1`，新档晨间版永远不满足；若同条件还用于普通版，则会卡住整章。

建议：入口依据“准备章已完成、当前待播主线17、到达`NextVisitDay`、甲线或乙线保护已落实/回退条件”等既有结算资格；母亲状态仍在同章结束时写入。晨间和普通入口共享章节的占用与完成记录，不提前写安全来绕过循环。

证据：设计第128～134行；`src/MaidStory.cs:264`及`:273`；`src/StoryDirector.cs`的`PendingChapterForDay`；`src/VanillaEleanorBridge.cs`。

此处也纠正了上一份机制汇总对“原版救母确认”的混称，已只修正该汇总对应说明。

### P1-2：D方案1同样需要明确的外出与跨夜协议

设计第214行把“最后访客、演完再关店、占当晚外出”标为低风险，第217行仍允许选择是否接受不占外出的不一致，但第262、444行已经把“消耗当晚外出、夜间各执行一次”写成确定承诺。两者尚未成为同一份确定规则。

原版`StoreShutterButton.EndAndClose`会重设`visitLeftTonight=1`、重置外出伤势/疲劳相关标志、打断对白并延时清场；不能在白天改一个外出标志便假定关店后仍然成立。原版跨夜实际入口还包含`EndNight`、事件日终、`BeginDay`、终局检查和保存，不等于只调用一个夜间方法。

最后访客本身有可行基础：原版日客队列有限，生成之后可安排尾部来访。仍需约定后续插队、玩家提前关店、自动叫号开启、她已入队但未到场时读档等规则，不能视为仅替换开场文字。

建议：方案1保留为优先原型，但风险按“中，需完成场景与日终协调”估计。明确外出预算在哪个原版边界消耗、由谁交还关店/睡眠，以及按游戏日和事件阶段判定是否已过夜。**方案1与方案2都覆盖**邀约中、接受后、赴宴中、演完未过夜、过夜未发报五类恢复边界。第446行目前仅要求方案2覆盖，范围过窄。

原型通过前，选项说明中的时间成本标为待定，不把“仍可再外出”保留成正式验收规格的另一种解释。

证据：设计第210～217、259～265、440～446行；`dist/special-mechanisms/StoreShutterButton.cs.txt`的`EndAndClose`；`dist/interaction-ball-review/EndOfDayUIManager.cs.txt`的`OnEndDayButtonClick`；`dist/scav-assistance/PlayerStore.cs.txt`的`GetNextClient/EndDay`。

### P2-3：A把可重试的中间状态列成互斥最终结果

设计第56行说三段反馈各取一个，第82～88行是“本次没接受、继续尝试”，第98行又要求同业务只取最终结果。若玩家先失败后成功，该取哪段并不明确；若在现有业务收尾时才播放“那就再看”，业务已结束，不能真的再试。

建议把最终结果收敛成“完成估价”“未完成退出/耐心耗尽”两种；若保留重试对白，作为业务中的独立一次性短反应，另记`retryReactionShown`，不替代最终反馈。第25章分支只依据教学反馈实际读完的事实，不按一个临时失败标记判断。

证据：设计第56、82～98、433行；原版`AppraisalServiceHelper.OnEstimate`；当前`src/MaidBusiness.cs`的`AttachAppraisal`和`BusinessAppraisalExit`。

### P2-4：原版“接受估价”不足以证明教学台词里的价格关系

设计第74～80行只要原生接受，就播放“我写得比你高”与玩家校正依据。原版会依据估价师等级接受不同精度的报价；`IsAppraisalAcceptable`的初始范围为真值50%～150%，之后再受等级精度门槛约束。接受并不等于精确，也未存储埃莉诺事先写下的数字。

因此高估但被接受的报价仍可能被写成玩家纠正了她的高估，而文案没有可核实的比较对象。第19章原有记录“这次没有用手盖住”，紧接新句“写在背面，你先别看”也需要说明是另一件估价物，避免看起来又倒退到遮掩。

建议优先使用不依赖高低比较的台词，例如她承认自己原本把卖相与本值混在一起；若保留明确比较，就定义她的预估值、读取原生提交值/精度，并为明显偏高、偏低和精确估值分别提供一致回应。首次称呼仍与估价表现无关。

证据：设计第64、74～80行；`dist/transaction-mechanisms/AppraisalServiceHelper.cs.txt`的`IsAppraisalAcceptable/GetEstimatePrecision/OnEstimate`；当前`Content/maid_v05.json`的`m19_b001`。

### P2-5：A第25章的接入点不能只依赖样品已领取分支

设计第102行强调回应与领取样品无关，但第104行只指定插在`m25_b003`后。当前`CreateReturn25`在`sample.claimed`为false时改用`sample_later`，根本不会构建`m25_b003`。按字面插在该块后，未领取样品时会漏播，并容易被误记为已经处理。

建议明确为“样品已领取/未领取两个分支汇合之后、共同`m25_b004`之前”；保留条件只检查第19章实际发生并读完的教学结果。补充交叉验收：第19章成功/未完成 × 第25章已领取/未领取 × 中途读档。

证据：设计第102～124行；`src/MaidReturnStory.cs:110`。

### P2-6：第二次邀约的延期规则尚未闭合

设计第299～304行把第二次约在“明晚”，冲突则“顺延一天并重新确认一次”；第267、436行又限制邀约次数为0～2，第442行阶段列表没有“次日预约已接受/发生冲突/等待再次确认”的明确分支。重新确认是否算第三次邀约、连续冲突怎么办、到场前主动改变主意怎么办，执行者仍需临场补规则。

叙事上晚会已经定日，人物不能因玩家店内事件就把同一场晚会改到后天。

建议明确：重新确认不计新的正式邀约次数；被强制事件占用视为该场未成行，等待下一场可用晚会，重写对应时间措辞；给预约确认和演出恢复独立标志，并允许玩家在真正离店前取消当晚安排。若想采用简单的一天顺延，应把事件写成可协调的私人邀约，而非固定日期的晚会。

证据：设计第267、297～317、436～446行。

## 较小的文案与基线问题

- B晨间开场把“母亲”换成“她/人”，在跨两天见面时又恢复了原先想解决的指代问题；建议第一句直接说“母亲”。甲线接回原块第二句“已经接出来了？”又重复前面已确认的内容，应按实际整段顺读调整，不宜机械只删首句。
- 第54行写旧伤和解在估价前；当前`CreateGrowingCloser`将旧档兜底和解放在估价后的wrap中。若不主动重排，应修正文档的当前结构描述。
- 替换估价引导时保留“配给站有人托带来问价”的关系，否则失败反馈“对方没认”里的第三方突然出现。
- 晚会“和上回一模一样”并非第26章两个选项的逐字回收，改“还是上回那个意思”或复用玩家实际选过的句子更稳。
- 基线表的44组对应上一项拾荒修改；当前连同现金优惠的基线为47组。它们都是现有功能的离线回归，不是本设计已通过的验收。
- 礼服双画风、缺图回退和只在事件内使用的原则合理。需要新增礼服专属场景白名单与读档修复，现有`PortraitCompat`不会仅凭相同命名自动继承女仆装的全部限制；这一工作已在改动范围内，应纳入具体验收。

## 创作质量

值得保留：

1. A让“受过帮助”通过后来的做事方法回响，且失败不锁称呼，人物依赖没有变成考试奖励。
2. C明确区分第一单客户、600预算商单和绕过她的采购商，也没有把询价误写成又获得一笔订单或新收益。
3. D放在第28章后的自由选择之后，强调她在上层区公开承认恋人身份。与公开场合不叫私下称呼的现有约定相容，玩家在生意判断上自信、她在社交与舞步上从容，双方各有所长。
4. 管事回收已有矛盾，高潮靠公开承认和合作原则成立，没有新增必须击败的情敌或羞辱人物。
5. 不加数值门槛、不重复发分红、延期次数有限、旧档不冒认教学历史、先技术原型再做正式美术，这些约束有助于控制范围。

这份方案主要加强的是既有经营中的人物表现与一次可选后日谈，没有采用上份汇总中全部交易模式。此处的克制是合理取舍，不需要为“互动补强”再塞入以物易物或参数订单。
