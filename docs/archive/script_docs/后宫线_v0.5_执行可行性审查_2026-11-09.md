# 后宫线 v0.5 执行可行性审查

日期：2026-11-09。基线：工作区 manifest 0.81、当前 src / Content，以及本机原版 0.46D 游戏程序集。

本次只核对进度和计划，不实施剧情与机制改动，不修改原计划、配套参数、路线图和既有报告，不部署、上传或推送。

## 结论

**方案方向成立，可以进入接口验证和基础修复；尚不宜直接当作所有边界均已确定的发版规格。** 三档原生声望门槛、三件独立橱窗饰品、等待期间继续经营、分阶段日常和原剧情事实复用，都能落到现有项目结构。无需推翻方案或降低声望目标。

实现前应补充三类状态规则：旧档如何证明玩家确实接受过双恋、普通顾客消失后的来访账本如何关闭、旧晚会延期状态如何收束。小费还需要按实际原生结算顺序做原型验证。另有一项体验建议：在明确入线前检查原告白资格，避免玩家接受入口并投入经营后才被强制收束到朋友。

## 三、需要补齐或收紧的执行规则

### 1. 实现前必须列出旧档“明确接受”的证据表

计划第9节已经区分“自动 Entry=2”与“确实接受”，方向正确，但需要把“进一步实质行为”落实成可判断的键集合。

当前 `src/DualMigration.cs:25` 附近会在普通恋人读档时自动调用 `DualState.Accept(2)`，随后自动写 `scene.dr05=true`。因此 Entry=2、FeatureVersion=1、MigrationVersion 和 dr05 完成标记不能单独证明玩家选过后宫；尤其不能用“任意 scene.* 为真”判断已接受。

建议补表区分：

- 自动写入、不能算接受证据的键；
- 新入口明确选中后写入的 Entry=1 等真实证据；
- 旧恋人入口实际完成及后续真正双恋场景的证据；
- 已确认三人关系，必须保留的证据；
- 无法区分“刚接受但尚未完成场景”与“仅自动初始化”的旧状态。

最后一类不得猜测后抹掉关系或回放奖励。应保留世界和既有关系事实，在下一个合法节点做一次兼容确认，或采用文档明确规定的保守续接策略。新 schema 则单独持久化接受证据，避免继续依赖间接推断。

验收应特别加入：普通恋人读档后自动具有 Entry=2 + scene.dr05=true，但从未接受双恋；与真正接受后中断的旧档分别迁移。

### 2. 实现前必须定义“旧来访已不存在”时的预算和小费恢复

计划第3、9、12节要求保存来访 ID、预算余额、小费 S/T，也写了“没有存活顾客才释放失效占位”，但还应明确该分支的完整账本行为。原生顾客对象与普通队列不受上述字段的原生序列化保障，保存 MOD 账本不等于保存了客户。

建议明确两条路径：

1. **确有可识别的同一次存活来访**：恢复该次剩余预算与已付小费，绝不再次乘 1.3。
2. **该来访对象已不存在**：按已提交成交关闭旧账本，清理失效占位；不复活客户、不补发已付小费。此后同一个普通客户工厂生成的顾客视为新来访，分配新序号、重新读取陈列快照。

普通客户 identifier 是客户种类标识，不能当成跨存档唯一来访 ID。若决定恢复已经不存在的普通客户，则必须额外设计工厂重建、队列重建和预算恢复，这会明显扩大兼容范围；本方案更适合沿用原生消失/重建语义。

验收里的“花掉200后余450，重载不回650”需拆成“同次来访仍存活”和“旧客不存在、新客重新生成”两个用例，避免要求一个原生并未恢复的客户继续交易。

### 3. 小费 P0 原型应明确同步提交边界

计划第3节已要求防重入、交易去重和恢复，要求是完整的；目前还缺基于真实接口的实现协议。这属于 P0 应解决的问题，不能跳过原型直接进入 P3。

原生 OnItemBought 在现金入账前执行，且参数没有现成交易 ID。仅在该回调里先写“已付”再加钱，或每次回调都分配一个新 GUID，都不能证明一次性结算成立。

建议在 SellItem 调用范围内捕获实际付款及来访序号，待正常销售完成后，同步提交额外现金、S/T 和结算序号。保存应避开半提交区间；项目已有 MaidProjects 的保存边界可参考，但必须确认新保护与已有保护共同生效。异常中断不得当成成功销售发小费。

P0 至少通过：单笔、批发逐物、最后一笔耗尽预算、重复回调、回调内触发保存、恢复后客户不再存在。保留计划规定的公式、150上限、非复利、不扣客户预算和不额外增加声望计算权重。

### 4. 旧晚会迁移要覆盖延期与第二次邀请，不只已预约

计划第7节明确“新档取消改天/再次邀约，既有已预约旧档照约完成”，但当前 `src/GalaStory.cs` 还存在：

| 旧 Phase | 事实 | 建议兼容处理 |
|---:|---|---|
| 1 | 首次邀请尚未回答/完成 | 从当前邀请续接，使用新明确选项，不重复开场已读内容 |
| 2 | 已答应改天，等待 retry_day | 只兑现这一轮旧承诺；保留一次旧邀约续接，结束后不再循环生成 |
| 9 | 第二次邀请已经开始，尚未选择 | 续接这次选择；不重置成新首次邀请 |
| 3 | 已预约 booked_day | 保留约定日期，按计划履约 |
| 4 | 已进入晚会 | 保留 ball_line 游标并完成；不重新入场 |

Phase=2 与 9 的继续入口目前在 Light()。如果删除新档重邀逻辑时一并删除该入口，两类旧档会留下永远到不了的状态。可以保留仅面向迁移旧档的兼容分支，无需给新档重新开放反复推迟，更无需增加晚会场景。

### 5. 体验建议：原告白资格在入口检查，避免经营后才判朋友

计划第6节并没有漏掉 CanConfess 失败：它明确要求 dr05 不合格时收束为朋友。因此这是可执行但有体验风险的既定设计，而不是一个未定义的死锁。

当前 `src/StoryEngine.cs:375` 的资格除母亲安全和路线外，还要求：

- FairDeals + Discounts 至少3次；
- UncleReported / Rescued / ThreatRecorded 至少一项成立。

当前双恋入口资格没有统一检查这两项。只在入口泛称“仍需原有恋爱前置”，可能出现玩家明确选后宫、冲过50、拿到铭牌后，才在 dr05 被强制判朋友的情况。这与希望玩家清楚路线方向的体验目标有冲突。

建议保留原恋爱资格，在正式接受入口前检查并显示准确缺项。不满足时暂不开放明确接受，保留正常经营及原剧情；若其中某项已不可能补足，直接说明当前存档只能继续朋友路线。兼容旧档或途中状态变化时，再保留 dr05 的合法朋友兜底。它不应变成进入后宫后的隐藏第四门槛，也不需要取消原资格。

## 四、需要一句话定准的细节

- 第8节“G3关系正式确认时转移未来拾荒资格”应拆开：G3 放行在 dr13 之前，三方关系确认在 dr17。建议明确以 **dr17 实际确认提交** 为切换点；已经激活的拾荒事件自然结束，历史来源保留，不靠清除全部旧收益标记处理。
- 第11节应给最终结算补一张“未确认 / 已确认但后半未完成 / 全部完成”的结果表。E4/E8 的三方确认条件与编号保持稳定；dr17完成但dr20未完成时，尾声不得写成共同晚饭等尚未发生的事实，完美标签也应与维护规则统一。
- 第二、三饰品还没列出最终 sprite 来源，但已有复用铭牌纹理的明确降级方案，**不会阻塞基础开发**。具体资源清单应在物品接入前冻结。
- 50/100/150 已确认不受原生上限阻挡，但“可达”不等于“节奏已经合理”。仍按原计划记录实际营业天数、成交净利润与10营业日增益，不未经确认更改声望目标。
- 本次变更同时涉及普通告白与侍从晚会，不只是 Dual 模块；原计划要求保留非双恋回归是必要的，不能因标题叫后宫线而省略。

## 五、推荐执行顺序与完成边界

1. **P0：部分已完成。** 本次补足了环境、声望标度、预算方法、回调顺序和原生持久化字段的静态证据。仍需真实到店/结算/存读档原型；先把上述状态规则写进计划和验收。
2. **P1：可以开展。** 先修原节点事实接管、重复告白、真实售货、朋友状态、文本缺块与统一场景完成。不必等待三件饰品全部接入。
3. **P2：在接管稳定后开展。** 接门槛锁存、六段阶段日常、迁移和最终结算。确认未达标时原客户正常营业、原主线不能绕过门槛。
4. **P3：以原型通过为前置。** 接三件物品和真实经营效果，先单个客户，再完整白名单；不把能编译作为现金/存档正确的证据。
5. **P4/P5：按原计划完整执行。** 同步中英文、阅读稿、运行图、维护说明；补真实状态测试与非双恋回归，再交实机验收。当前参数 JSON 与主计划的三个门槛、首轮效果参数没有发现冲突。

本次审查不把 v0.5 标为已实施，也不把 0.81 标为工坊已发布。补齐上述边界后，这份方案具备进入开发的条件；发行完成仍应以新构建、真实机制验收与实机记录为准。
