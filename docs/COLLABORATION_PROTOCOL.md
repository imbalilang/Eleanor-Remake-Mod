# Collaboration protocol（协作执行规则）

这份文件记录的是一条用户明确要求的工作规则，不是项目世界观或文案规范。它来自 2026-11-22 的一次真实失误：用户指出某个内容与目标无关、应删除；我连续四轮只做了重命名、加边界说明、逐文件补删，直到用户再次指出才彻底清掉。

## 1. 明确的删除要求：先删，不要先解释

当用户说“删掉 / 移出 / 不要放 / 无关”时：

1. **先执行删除**，不要把删除改写成“重命名”“降级”“加一段说明它在范围外”。
2. 删除后立刻在目标范围内全局搜索同义残留，而不是只改用户指到的那一个文件。
3. 报告完成时给出证据：改了哪些文件、搜索了什么、结果是否为 0 处匹配。
4. 如果认为不该删，**先问一句**，不要先改一半再解释。

反例（这次发生的）：

- 把“仍未修的硬点”改名为“已知局部缺陷（不等于 AI 感根因）”——没有删。
- 把清单换成“这类问题不纳入本咨询包”——仍然点名，仍然把读者引过去。
- 只删了 `08`，没有搜索 `02/04/06/07` 里的同一句。

## 2. “删除”的完成标准

删除的完成标准不是“我解释了它为什么不重要”，而是：

- 目标范围内搜索不到该内容或其同义变体；
- 没有“虽然不重要，但……”式的残留脚注；
- 相关索引、摘要、目录里的引用也同步移除或改为不指向它；
- 如果删除影响构建/验证，构建/验证通过。

只改主文件、留下目录引用或历史摘要，不算完成。

## 3. 用户指出错误时：先修，后说明

用户指出问题时，默认他要的是**修正结果**，不是听我证明自己的判断合理。

- 先改，再用一两句话说明改了什么；
- 不要用“我当时的考虑是……”来替代修改；
- 不要把“我承认”写成一段新的辩护；
- 如果确实需要解释设计取舍，放在修改完成之后，并明确它不是不修改的理由。

## 4. 不做“部分服从”

对同一类问题，一次处理完所有同类位置：

- 先搜索全范围，列出所有命中；
- 一次改完，再复查；
- 不要把“当前文件改好了”当成“问题解决了”。

这次四轮对话的根因不是用户没说清，而是我每次都只处理“眼前这一处”，没有把“全包搜索 + 一次清干净”作为默认动作。

## 5. 不要用“范围外说明”保留内容

“这不属于本包，不展开”仍然会把内容放进读者视野。如果它不属于目标，正确做法是**不写**，不是写一句“它不重要”。

判断标准：**如果它不服务当前目标，就不应该出现在当前交付物里，也不应该加脚注。**
