## 3. 问题D：王尔德项目提前可见、可购买

### 3.1 可见性规则（新）

王尔德列表里只出现“当前这一步”和“已经做完的步骤”。

| 剧情状态 | 列表中显示 |
|---|---|
| 未入侍从线、约定已解除、关系已终止、版本不支持 | 七项全部隐藏 |
| 已入线，母亲尚未安全（第16章前） | 全部隐藏 |
| P1 可购买 | 仅 P1，可购买 |
| P1 已付、结果未播放 | P1 显示为“已结清，等待她来访” |
| P2 可购买（第23章完成且 P1 结果已播放） | P1（已结清）＋ P2 现金方案 ＋ P2 人脉方案 |
| P2 已付 | P2 只保留所选方案，显示为已结清；另一方案隐藏 |
| P3、P4 | 同 P2 |
| 约定在中途解除 | 已付项目保留为“已结清”记录；未付项目全部隐藏 |

可购买的方案若资源不足，仍显示，购买时提示缺口（现有逻辑）。前置未满足的项目一律不显示，不再使用“前置条件说明”占位。

每当一个新项目出现，发送一次通知：“王尔德那里多了一项筹备：××。”第16章、第23章、第24章与第26章完成时各一次，读档不重复（用 `MaidState` 标志去重）。

### 3.2 修复项

1. **默认隐藏**：注册时隐藏参数改为 `true`，运行时副本状态默认为 0。即使刷新晚到，玩家也看不到。
2. **按项目判断可见性**：`RefreshStates` 用上表计算每个ID的 `hidden` 与 `state`，不再只看 `HasHistory`。运行时副本与定义同步更新。
3. **刷新时机补全**：
   - 读档与新开局时照常调用；新开局另在商店就绪后（第一次 `OnGenerateCustomerVeryEarly` 或开店时）再刷新一次，并去掉对 `StoryActive` 等的依赖。
   - 每日刷新移到 `OnGenerateCustomerVeryEarly` 的所有提前返回之前。
   - 打开王尔德界面时刷新：为 `WildUIManager` 与 `WildNetworkUI` 的打开、重建列表方法加前置补丁，具体方法名在实机核查时确定。
   - 改变 `Available` 的剧情节点结束时刷新：第16章、P1 结果、第23章、第24章、第26章、约定解除、关系终止、第20章表白。
4. **购买入口全覆盖（实机核查后实施）**：在当前游戏版本的程序集中列出所有调用 `NetworkUpgrade.Unlock` 的方法，以及所有为网络升级扣 `wildFavor` 或现金的方法，对其中每一个都只拦截 `er_maid_` 前缀的ID，交给 `MaidProjects.TryPurchase`。原版升级照常走原逻辑。
5. **解锁兜底**：为 `NetworkUpgrade.Unlock` 加只针对 `er_maid_` 的前置补丁。只有 `TryPurchase` 提交成功后发出的那一次通知性解锁可以通过（事务内设一次性放行标志）；其他来源一律阻止，记录“未经事务的解锁”诊断（调用栈、ID、当日），并立即按第3.3节退款。这一步保证即使将来游戏更新新增入口，也不会再出现“直接解锁”。
6. **回归用例**：新增“新开局未入线”“已入线未救母”“已入线、P1 可购”“P2 已付”“约定解除”五种状态下的列表可见性与每个入口的购买尝试。

### 3.3 已受影响存档的修复

读档时检查七个ID：若原生状态显示已解锁，而 `MaidProjects.Paid(p)` 为假，判定为“异常解锁”。

- 恢复为第3.1节规则下应有的状态（通常是隐藏）。
- 按读档时的原生报价 `GetCost()` 退回现金。原生购买时用掉的 wildFavor 比例无法事后还原，统一退成现金；报价若因折扣变化与当时不同，以现报价为准，并在日志写明。
- 每个ID只修复一次（`repair.p{n}.{plan}` 标志），日志记录ID、退款额、当日，弹一次汇总通知：“埃莉诺的筹备项目此前被提前解锁，已撤销并退回 ×× 信用点。剧情进度不受影响。”
- 不把异常解锁视为已付款，不触发剧情结果，不改动派系声望。人脉方案若被原生直接解锁，原生不会扣声望，因此无需退声望。
- `Paid(p)` 为真的正常购买不受影响。

### 3.4 验收

- 新开局、未入线：打开王尔德两个界面都看不到任何 `er_maid_` 条目；用调试入口强行调用每个已知购买方法，余额和解锁状态都不变，日志出现诊断。
- 入线后、第16章前：看不到条目。第16章完成后只出现 P1，同时收到通知。
- 已付 P2 现金方案：列表只剩 P1、P2 现金方案（已结清），P2 人脉方案消失。
- 用 0.68 制作的“开局已解锁 P1、P4”夹具读档：两项被撤销，退回金额等于读档时报价，只通知一次，再读档不重复退款。
- 原版升级的购买、折扣、wildFavor 抵付、统计全部回归不变。

## 4. 问题C：暂缓存档迁移

规则（读档时执行，幂等）：

- 条件：`MaidState.Active && MaidState.Confession == 3`。
- 写入：`Confession = 1`，`RomanceState.Romance = 1`，标志 `migrated.deferred = true`。
- 通知一次：“主从恋爱已确认。”（与第20章选择一的提示相同）
- 之后的效果：`MaidState.Lovers` 为真；第23章完成后 P2 可按正常规则开放；日常与尾声按主从恋爱处理。

衔接处理：
- 若第21章（莉迪亚）尚未播放：按主从版本播放，无需特殊处理。
- 若第21章已经播过暂缓变体（`m21_b008`，莉迪亚说“别的她没让我问”）：第22章跳过开头追问莉迪亚的那一段（现 `m22_b004`，“莉迪亚前两天是不是来问你了”），直接进入吊坠段，避免与已播内容矛盾。判断依据为 `migrated.deferred` 加上第21章已完成。
- 第22章不会再出现再次确认菜单，代码中的 `Confession==3` 分支整体删除；迁移在章节构建之前完成，确保不会构建出已删除的分支。
- 读档顺序：放在 `MaidRouteMigration.OnLoaded` 之后、`MaidProjects.OnLoaded` 之前，让项目可见性按迁移后的状态计算。

验收：分别用“第20章刚选暂缓”“第21章已播暂缓变体”“第22章正在进行中退出”三种夹具读档三次；每种只迁移一次、只通知一次，第22章内容与已播内容不矛盾。
