# 主从恋爱路线 v0.2：完整改动计划

日期：2026-11-07。状态：设计与本地代码核对完成，尚未实施运行时代码、英文、美术或发布。

对应全文：`docs/全流程攻略_纯阅读版_大小姐侍从恋爱线_设计稿.txt`，现为 v0.2。本文所有新费用、阶段、状态名及代码拆分均为拟议方案；“已核对”一节才描述实际存在的接口和行为。

## 1. 本次明确的方向

保留原有普通恋爱，新增一条具有长期投入、女仆形象和上层区归来结局的主从恋爱路线。800是入场，不是买到全部剧情的总价。

玩家以当铺经营积累的资金和人脉，帮助埃莉诺安顿生活、重新进入上层区、形成实际业务能力、获得公开认可，最后拥有独立事业。她在比过去更有能力、更受尊重、可以自行选择生活的情况下，仍选择回到下层区主人身边。玩家的投入、判断和地位反差需要在每一步得到具体反馈。

“比过去耀眼”具体表现为从依赖母亲地位的富家千金，变成以自己名字获得业务与尊重的人；不直接宣称她已经比空间站最大水培农场更富有，也不让玩家八百块颠覆整座空间站。

实现边界：原生柜台对白、交易、原生王尔德升级列表、兼容立绘与少量存档状态。不得新增公司经营、上层区地图、雇员控制台、每日服务费或自动经营。新增六次结果来访和必要旧档承接，不抢占同一天的普通经营流程。

## 2. 已核对的本地依据

核对范围为当前工作区、本地 `dist/workshop-0.61` 至 `dist/workshop-0.66` 中的 `EleanorRomance.dll` 和安装游戏的 `Probably Stolen_Data/Managed/Assembly-CSharp.dll`。0.66核对了完整相关回调，0.61～0.65比较了调查款回调与调度入口。采用源码及只读 IL 检查，未启动游戏验证 UI，也未读取或修改玩家存档。不能据此宣称已经覆盖所有线上历史包。

| 项目 | 已确认事实 | 对方案的影响 |
|---|---|---|

历史包差异：本地0.61～0.65同样有调查款回调写恋爱状态、推进章节且没有付款调用，但其 `OnGenerateCustomerVeryEarly` 没有0.66的 `RomanceLocked` 检查。不能推断这些版本都停在章13，也不能自动把已经推进到后面的恋爱关闭档倒回入口。它们升级到0.66后才停住、或已进行其他选择的情况，需要分别制作夹具。

本地包比较不是“整个线上所有版本”的证明。发布前必须按线上实际包清单和真实存档补齐迁移样本。

## 4. 五阶段挑战与经济方案

以下全为首轮平衡假设，暂未跑真实经营周目。费用不写死在对白里，界面使用实际报价。

| 项目 | 首款基价 | 现金尾款基价 | 人脉尾款基价 | 声望支付时门槛／实际扣除 | 结果 |
|---|---:|---:|---:|---|---|
| P1 安顿与衣装 | 600 | 600 | 无 | 无 | 母女安顿、专属衣装 |
| P2 重返上层区 | 1200 | 1200 | 400 | 下城区≥30，扣10 | 女儿合法通行与介绍 |
| P3 独立业务准备 | 2000 | 2000 | 800 | 上层区≥40，扣10 | 能力、样品、小业务 |
| P4 正式亮相 | 3000 | 3000 | 1200 | 上层区≥60，扣15 | 展示、可信业务认可 |
| P5 自己的事业 | 4000 | 4000 | 2000 | 下城区≥60，扣15 | 登记、场地、启动资金 |

无折扣、无倍率、无抵付时：

- 五项纯金钱共21600，加入线800共22400。
- 全选人脉：五项共15800，加入线800共16600；下城区消耗25、上层区消耗25。
- 旧承接档豁免入线800，因此同条件总计21600或15800；不补发800现金。
- 声望门槛是支付当时门槛，扣除后不要求仍维持原值。例如P4支付时上层区60，扣15后45合法；已完成项目不随声望下降失效。

### 4.1 为什么这样收费

P1是入场后的第一项清楚可见的兑现，成本较低。P2、P3使她重新进入社会并具备工作能力。P4、P5是明确的高投入目标，其回报是认可、事业和主动选择，不是可滚雪球的固定收益。

人脉路径让玩家用既有经营路线换取较低现金成本；纯金钱路径确保敌对或低声望玩家仍可推进。四处声望消耗都必须在确认前显示，不能在演出结束时突然扣除。

### 4.2 分期、延期与抵付

- 每项目两次成功支付，五项总计十次支付；不做任意金额滑块或新分期界面。
- 首款固定，尾款才选现金或人脉。首款后声望跌了，直接改付现金尾款，不撤回项目重来。
- 已付首款永久保留到该存档结束，无利息、催缴倒计时、停留扣好感或母亲死亡风险。
- 王尔德原版 `wildFavor` 允许抵付现金部分，优先级沿用原版。它与派系声望是不同资源；菜单分别说明，不把wildFavor伪称为已消耗派系声望。
- UI标示原生最终报价；记录 `QuotedCost/CashUsed/WildFavorUsed/ReputationUsed`。题设基准总额不是每局必然消耗的现金量。
- 升级折扣、难度变化时，仅未付部分按当下报价；已成交不补差价、不退款。
- 支出为可选高难路线成本，会与玩家原版升级预算竞争；“不改变主经营进程”表示不替玩家经营、不强制停业、不改原版任务，并不表示完全没有机会成本。

### 4.3 平衡验收而非武断保证

用正常经营样本记录第39／59／75天的现金、库存价值、派系声望和可自由支配收入。至少覆盖新手现金紧张、稳定盈利、高收益、人脉型、低声望五类测试。

观察每项目需要的额外经营天数、是否逼迫变卖核心经营资产、尾款低于日常可用余额的频率、声望扣除实际失去哪些待遇。若多数正常盈利玩家仍需几十天只为等钱，应先调P4/P5基价或分期结构，不用送回全部投资消解挑战。

初步体验目标是每项需要做准备但有可见进展；第29章可落到约第75天或更后，而非保证所有玩家都在75天完成。必须在真实样本后才能承诺具体难度。

## 5. 王尔德接入设计

### 5.1 注册与显示

优先使用本机已确认的 `ModHelper.AddNetworkUpgrade`。项目ID统一用 `er_maid_` 前缀，例如 `er_maid_p2_deposit`、`er_maid_p2_cash`、`er_maid_p2_favor`。

五个首款、五个现金尾款、四个人脉尾款，共14条定义，按阶段显示或禁用。每阶段只允许首款一次、尾款两种支付方式二选一；对外仍是既有升级列表，禁用原因和已付状态使用已有说明区域。

需求是与当铺升级并列，默认选原有升级页的适当tab，不新开应用界面。需实机确认默认tab位置；不可选原版 `Advanced` 导致未付房产的玩家看不到项目。

未来阶段以说明预告，不允许跳过前一结果来访购买。未入线或无资格时隐藏本MOD条目；若原生刷新无法可靠动态隐藏，可保留禁用条目并明确“未开启此路线”，不可影响普通升级。

只在加载注册和新档初始化时稳定注册定义，避免每帧移除再加。旧档用 `AddMissingAfterLoad` 补入本MOD定义，保留所有原生购买状态。定义与运行时副本同步要有测试。

### 5.2 购买事务

原生onUnlock不能作为唯一校验点。为两个购买按钮入口增加只针对 `er_maid_` 的拦截，由一个统一事务函数负责：

1. 根据真实当前选中ID找项目，不信任UI上一次的缓存。
2. 检查路线仍有效、前置反馈已完成、首款／尾款未完成、无重入事务。
3. 读取当前实际报价、现金、wildFavor和相关声望；复核门槛与资源足额。
4. 在已有说明区域确认最终金额、抵付与声望变化，购买点击本身即确认；无弹窗套弹窗。
5. 同步提交本次资源变更、项目账本与升级状态；记录一次交易标识，回调、统计及通知各触发一次。
6. 禁用同阶段另一尾款方案，刷新已有UI；仅设“结果待来访”，不当场宣告她已通行或已开业。

失败必须在任何扣款前返回；异常发生在提交途中时恢复事务前的相关余额与本项目状态，不重置其他升级。同步提交期间禁止重入；不要在扣现金和扣声望中间yield、异步等待或触发可保存对话。

还须检查原生声望事件、解锁事件是否会触发保存或再次调用购买。无法保证单次提交时，应增加可恢复事务记录并证明恢复不会重复支付；不能仅靠一个bool宣称崩溃后事务绝对安全。

保存后读档以项目已提交记录为准修复本MOD显示状态，不再次扣钱。遇到“项目与原生条目状态矛盾且无法确定是否扣款”的损坏档，保留账本、停止该项目重复支付并记录诊断，不能猜测再扣一次。

原版ID走原函数不变；原本升级、折扣、wildFavor、统计都必须回归验证。本MOD不覆盖全局 `NetworkUpgrade.Unlock` 的行为。

## 6. 日程、等待与不锁死玩家

主剧情仍用现有章节推进。筹备阶段单独记录，不把阅读章24当作现有代码章24——现有代码24对应阅读章23。

推荐：基础关系完成时沿用原章300作为核心完成，新增 `MaidProgressChapter` 管理阅读24～29，调度器在普通后日谈之前检查该分支；不要简单使用大于300的新主章号，否则现有 `Chapter>=ChapterComplete` 会直接终止调度。

| 事件 | 前置 | 最早相对间隔 |
|---|---|---|
| P1可付款 | 母亲已安全、侍从方向仍有效 | 当场结果完成后开放 |
| 阅读24 | P1尾款完成、阅读23完成 | 距阅读23至少2天；付款后至少下一可用日 |
| 阅读25～28 | 对应尾款完成、上章结果完成 | 距上个结果至少3天；付款后至少下一可用日 |
| 阅读29 | 阅读28完成、主从恋爱仍确认 | 至少2天 |
| 等待短聊 | 主从恋爱确认、项目未齐、没有结果待播 | 共用后日谈冷却，每阶段至多一次，至少7天 |

队列优先级：原版紧急事件／已在柜台的访客→原有救母桥接→旧档承接／共同剧情→已满足条件的项目结果→等待短聊／日常。每个游戏日至多排一次本MOD重要来访，不清空其他访客抢位。

结果仅在完整收尾后完成，排队与到店都不是已完成。关店、中断、读档后恢复同一结果，不重复首秀、开放两次项目或重发物品。

旧档已到第80天、100天等情况采用当前日相对间隔，不拿目标第41天判断过期。已在无尽模式继续的有效MOD档应可推进，不能沿用仅针对原版首次接管的“无尽不接管”条件误拦截；是否可运行须实测。

游戏本身结束仍正常结束。筹备未完就结束跑局，追加实际阶段尾声；不跨新周目继承资金、不暗中延长原游戏，也不谎称尚未完成的事业已经成功。

| 首秀之后私人侍从日常 | 女仆图 |
| 仍在等待首秀 | 常服，不能仅凭已付款偷跑首秀 |
| 悲剧、革命、正式退出、紧急救援 | 原场景立绘 |
| 未启用少女当铺／资源缺失 | 原始场景立绘或其可用美化版本 |

解析条件是 `IsBeautyActive && LocalSpriteValid && AppropriateScene && (DebutCompleted || IsDebutScene)`。不要把女仆图绑定到所有 Eleanor sprite key 的全局替换。

`SanitizeLoadedClients` 补本地女仆键回退，覆盖队列中与当前显示对象；重建SpriteDict后重新注册有效资源。存档保存逻辑服装与场景，不把图像存在性当剧情进度。

少女当铺中途停用：进度保留，下一次读取或刷新安全回原版；再次启用后仅合适场景恢复。资源缺失只记录诊断，不关闭剧情或弹强制错误对白。还需实测少女当铺自身后置替换是否覆盖本MOD局部键。

## 8. 已有线上存档的自然续接

### 8.1 迁移目标与边界

本次明确支持已确认的“800提议完成→代码第13章→恋爱锁定→无后续”的旧档。玩家看到的是埃莉诺回来继续谈条件，不是让他重开周目或回滚交易。

技术上它是对旧停线状态的定向恢复；游戏内用新增序章承接。发布说明可写“新增800提议的后续路线，已有该选择的存档可继续”，不虚构旧版实际已经预留完整线路，也不把当时已播放的拒绝改写成她早已接受。

### 8.2 候选识别

对本地核对的0.66状态形状，可采用以下联合条件作为首批迁移候选，而非单字段命中：

- MOD已初始化、当前受支持版本、Schema=2、非保留原版的 `OldBlocked` 档。
- `Chapter==13`，`PendingChapter==0` 是直接完成该选项的基准样本。
- `Romance==4`、`Route==0`、`BetrayalKind==0`、`DriveState==0`。
- `MotherState==0`、尚未MotherVisited、尚未EpilogueDone，调查Savings已到800。
- 无正在等待的保释／拘捕流程，无已完成核心或其他明确终止记录。
- 尚无新路线状态、迁移标志或已执行过的承接序章。

这些条件依据已核对控制流推断，不是旧档中确有一个“选了800”的显式历史标记。必须以真实存档／各发布包导出的夹具验证碰撞，不能声称只凭这组字段绝对还原所有玩家行为。

`PendingChapter==13` 或已经出现数据盘访客等非基准状态：单独核验历史版本与队列，不能宽松并入通用规则。若确认仅为旧排队状态，重建本MOD单一访客；不得清空整个队列。

有背叛、数据盘已处置、路线3/4、玩家已选保留原版、游戏版本不支持或存档版本未知的档，不自动恢复。本次代码中其他剧情锁定问题须按结束原因另行分类，不用“全解锁”处理。

### 8.3 迁移步骤

1. 正式发布前保留样本存档和发布包哈希；实际运行迁移前把相关旧字段写入本MOD迁移快照，不清除原ModData。
2. 在游戏数据加载完成且 `InitializeForSave` 已执行后、任何 `RomanceLocked` 队列早退之前检测。旧schema不可简单改号放行。
3. 先记录 `Legacy800ResumeState=Pending` 与迁移版本、原字段快照，再仅对命中的状态解除旧通用恋爱锁定。
4. 保持主章13待接，专用承接状态优先安排旧约序章；NextVisitDay取当前日+1或下个安全来访时段，不能回填过去日期。共用每日排队限制。
5. 序章完成后记录恢复方向：主从或普通。主从记 `EntryPaymentKind=LegacyWaived`、实际支付0，不补扣800；普通继续原有关系。
6. 下一次可用来访进入代码章13的数据盘，不重置SavedCash、Savings、声望、吊坠、已有奖励或原版任务。
7. 保存后反复加载只恢复Pending或Completed，不再次播完序章、不再入账、不再改日期。序章中途退出则恢复该序章，不越过玩家选择。

对于未命中但疑似相关的档，写可诊断原因而不破坏原进度；收集版本与状态后补精确规则。无需玩家重开，但也不能保证尚未核对的所有第三方修改档可自动修复。

### 8.4 800历史账务

本地0.66明确未扣800。旧续接让她说“调查费我自己凑够了，不用现在补给我”，同时重新谈服务条件。旧玩家获得一次明确的入线豁免，新玩家仍在当场支付800；后五项目相同。

新状态必须区分 `Paid` 与 `LegacyWaived`，不要伪造累计支出800。若未来核对到某历史包确实扣过款，增加 `VerifiedLegacyPaid` 规则，不退款、不二次扣款，并保存证据来源。
